# 项目工程审查与维护

## 目标与边界

用于系统级或跨模块任务：全面审查、成熟度/差距评估、工程治理规划、维护性盘点，以及把审查结论转化为可验证的修复。不是要求每次改动都做全仓扫描，也不代替专项技能。

先判断用户要的是评估、实施、复核还是报告。用户只要求评估时不擅自改代码；明确要求修复时，先确认问题证据，再按影响范围实施。提交、推送、合并、删除分支仍须遵守用户本轮授权和 `git-pr-workflow`。

## 来源与证据

审查前检查分支、工作区、差异和适用的 `AGENTS.md`；保留既有改动。依据 [references/review-sources.md](references/review-sources.md) 选择当前权威文档和历史材料。

- 当前行为以代码、迁移、配置、脚本、CI 定义及本轮可取得的运行证据为准。
- 当前规范以 `docs/agent-baseline.md`、`docs/coding-conventions.md`、有效 ADR、领域文档和治理契约为准；冲突时记录冲突并按仓库优先级处理，不静默择一。
- `docs/archive/` 与带日期的审查、评估、验收材料只用于提取风险模式、复核问题是否复发及追溯当时判断。不得将其中的问题数量、待办、修复状态、测试结果直接宣称为当前事实。
- 每项结论标注为：已复现/有当前证据、待外部验证、历史案例、或改进建议。静态搜索、测试通过、模拟结果与生产验证不可互相替代。

## 工作方法

1. **界定范围**：明确模块、用户/数据边界、关键业务链、目标环境、时间基线和排除项。系统级审查要有覆盖表；不能用一次 grep 或单份旧报告代表全仓。
2. **建立事实地图**：从文档索引找到权威入口，再追到实现、调用方、配置、数据库迁移、自动化门禁和验证记录。遇到过期或互相矛盾的材料，标明来源和时间并查证现状。
3. **按适用性检查**：评估业务正确性与数据一致性、状态机/并发/幂等、租户与安全边界、模块与依赖边界、数据库和迁移、调度与时区、Worker/SDK/API 契约、资源/背压/容量、故障恢复、可观测与运维、构建/CI/供应链、前端关键工作流、文档与治理漂移。逐项记录“有证据 / 不适用及原因 / 未验证”，不机械要求每次覆盖全部领域。
4. **对抗验证**：针对高风险链路写出前置条件、触发步骤、状态/数据副作用和业务影响；优先复现并沿调用链确认根因。检查失败、重试、并发、超时、进程中断、旧 leader、依赖不可用和恢复场景。外部环境、真实负载或凭据缺失时明确列为未验证，不用静态推断代替。
5. **分层结论**：区分确认缺陷、回归风险、治理缺口、待验证假设和暂缓建议。每个发现包含位置、触发条件、影响、证据、修复建议和验证标准；避免仅凭“更通用/更标准”推动抽象或重构。
6. **闭环维护**：实施修复时同步受影响的测试、API/SDK 契约、运行手册、ADR、治理清单、索引和 changelog。当前待办只进入 `docs/analysis/todo-master.md`；历史报告保留其当时结论。只有实际执行成功的检查才记为通过。
7. **选择专项技能**：按 `references/review-sources.md` 路由到对应技能；只加载本任务需要的领域流程，避免复制专项规则或把一次系统审查变成无关全仓改造。

## 报告要求

- 先报告可操作发现，按严重度排序并给文件/行或可定位的配置证据。
- 对系统级审查给出覆盖矩阵、验证层级、未覆盖范围和外部验证需求。
- 说明基线 revision、实际运行的命令/测试及结果；“未发现可复现问题”不等于“没有风险”。
- 修复任务额外列出实际修改、回归验证和剩余事项；不要把历史报告中的结果写成当前验证。
