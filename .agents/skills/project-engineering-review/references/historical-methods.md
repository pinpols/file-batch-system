# 历史审查的复核与方案判断方法

<a id="ENG-1"></a>

## ENG-1 历史发现的证据分层与反例

适用于旧清单复扫、审计结论冲突或自动扫描命中。先把结论拆为触发前提、具体执行路径和可观察后果，再追当前入口、调用方、SQL/事务、恢复与实际用户影响；给出一个会触发的输入和一个相似但合法的输入。

- `@Autowired` 的搜索命中可能是构造器参数、可选依赖或注释；不能按文本计为字段注入违规。
- Outbox 在数据库回滚后重发可能是至少一次语义的正常结果；应检查下游去重和业务副作用，不能只因重复发送判为缺陷，也不能默认必须改 Kafka 事务。
- 表缺直接租户列、代码出现 ThreadLocal、存在多个 UPDATE 都只是线索；核实所有权链、实际跨线程路径和每条更新的不变量。不要把某张表的正确性策略推广为“所有 UPDATE 都加 version”。

报告区分已证实、待复现、合法例外和原结论撤回。原始报告内部自相矛盾时，记录冲突及所用证据，不从其中最醒目的“全修”句选结论。

<a id="ENG-2"></a>

## ENG-2 方案比较与替换范围

适用于调度器、IO模型、模块拆分或通用平台能力选型。用当前瓶颈和用户场景定义比较轴：解决哪一层、持久化/恢复不变量、兼容迁移、失败窗口、依赖与运行成本。保留继续使用现有实现及回退方案；以代表性数据证明收益后再选型。

旧 Wheel、全量异步IO、导出chunk拼接、分库方案均只是原时点候选。某候选后来弃选仍可提供比较方法，不能复活其部署步骤、旧schema或固定阈值。方案的弃选理由与后续实际实现分别记录；代码删掉某组件也不证明同类用户风险消失。

<a id="ENG-3"></a>

## ENG-3 修复后的横向复查

适用于多轮治理和跨模块修复。按失败机制聚类，再核对同构入口及修复新增代码：例如主状态CAS已保护，旁路摘要/发布状态是否仍可被旧调用覆盖；主认证链校验了时间，fallback链是否漏校验；新增模块是否进入守卫扫描。

复查前一轮标为合法/已修的代表样本，以及尚未覆盖的入口，明确变化是新缺陷、复发、规则变化还是原误报。历史评分、修复数、并发Agent数量不作为覆盖或完成标准；本方法不要求启动额外Agent。

<a id="CFG-1"></a>

## CFG-1 配置是否真正改变运行路径

配置字段/getter存在与运行分支生效要分别核对；完整取证、导入影响和快照/密钥生命周期方法已归入[配置治理](../../configuration-governance/references/lifecycle-methods.md)。本节保留历史方法ID和来源映射，不重复维护同一规则。

<a id="READ-1"></a>

## READ-1 机械整理的语义复核

适用于嵌套调用、长条件、构造与命名治理。只在有阅读收益时提取具名中间值；保留短路、求值次数和先后、异常时点、回调/轮询内的查询和惰性执行。简单getter与清晰链式调用不机械拆散。

参数对象和Builder改造要核对Jackson/MyBatis/Spring的构造入口、record canonical constructor、可见性和默认值，不能丢掉仍有消费者的无参构造。FQN缩短后核对同名类、包名和静态重载的绑定；解析通过或去注释词法相同只证明相应范围，不证明类型绑定和编译正确。参数阈值与例外使用现行编码规范，不能继承旧计划中的阈值。
