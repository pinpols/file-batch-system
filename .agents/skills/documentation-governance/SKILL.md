# 文档治理

## 方案、评审与治理留档

- 改造方案、架构/系统评估、代码或项目治理审查、整改计划和验收结论必须主动落到对应权威文档，不等用户逐次提醒；先查找并增补现有主记录。
- 方案进 `docs/plans/`，长期架构决策进 ADR；当前问题进入 `docs/plans/todo-master.md`；日期化评审/审计进 `docs/review/` 或 `docs/audit/`；验证结论进 `docs/testing/` 或 `docs/verifications/`；运行操作进 `docs/runbook/`。
- 说明基线、范围、证据、结论、优先级、未验证项和下一步，并区分方案目标与代码已实现事实。新增长期文档时同步索引；简单日常任务不新建文档。
- 评估和审查只记录发现与建议，不自动扩大为实施授权。Changelog 记录规范或产品变更摘要，不替代方案、审查或验收正文。

## 信息架构

- 根 `README.md` 要让新人一眼知道项目解决什么问题、核心架构、怎么启动/验证、去哪里找更细文档。
- 一级目录索引覆盖二级目录即可，不要把所有文档扁平展开；新增目录或长期文档必须登记到相应索引。
- 当前事实、设计决策、运行手册、验收报告、压测结果和历史归档要分开。不要把一次性验证报告写成长期设计真相。
- 归档文档可以保留当时结论，但若存在明显误导、术语不专业或链接失效，也要加注或修正。

## 日期与 Changelog

- 持续维护的规范、架构说明、运行手册通常不在文件名中带日期；一次性验收、压测、审计和里程碑报告应带日期并按归档策略管理。
- 根 `CHANGELOG.md` 记录面向用户、部署、生产行为、契约、安全和重要缺陷的变化；`docs/changelog.md` 记录文档/基线类变化，按仓库约定同步。
- 代码行统计使用不带时间戳的当前快照，并把历史快照放入 archive；不要用旧报告覆盖当前状态。

## 漂移检查

- 修改文档、脚本、目录或生成物后，运行适用守护，例如文档索引、时间戳策略、链接/引用、Changelog 同步、LOC 快照和 README 检查。
- 文档中的命令、路径、环境变量和开关要与实际脚本/配置对齐。
- 对“已验证”“已上线”“全绿”等结论保留证据来源；没有当前证据时写成历史记录或待验证项。

## 评估与审查报告

- 核对结论时记录评估日期、代码基线、范围/排除项、方法和可复核证据。
- 分开陈述设计覆盖、代码实现、自动化测试、真实依赖/目标环境验证；不得把模拟或静态检查提升为生产能力证明。
- 容量、可用性、安全和生产就绪结论必须给出环境、负载/威胁模型、验收标准及限制。
- 历史评估保留当时结论并明确日期；新代码或 CI 事实变化后，标记过时结论并链接当前权威文档，不把旧报告继续当现状。
- 能力评估必须区分方案设计与实际交付，未完成或未验证项应与当前待办入口一致。

## 写作质量

- 用业务和工程通用术语描述，不使用生涩、机器感或内部临时口头语。
- 保留必要约束，删掉过期计划、重复索引和无主残留文件。
- 复杂治理主题优先写结论、适用范围、操作入口和验证命令，而不是堆叠背景叙述。
