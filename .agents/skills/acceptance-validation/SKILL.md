# 验收验证

## 选择验收范围

1. 选择步骤前先阅读 `docs/runbook/be-acceptance.md` 和入口脚本的当前用法；runbook 与可执行脚本是参数、步骤顺序和行为的权威来源。
2. 确认用户要求的范围：定向测试、完整验收、仅严格校验、仿真或压测。没有必要时，不要把定向请求扩大成耗时的全量运行。
3. 核对构建版本、必需服务、端口、磁盘和仓库状态。区分应用运行时与基础设施依赖；若应用本地构建运行、依赖由容器提供，应如实报告。
4. 测试共享本地数据库、端口、消息代理或 worker 进程时优先串行执行。只有用户明确要求并行，或已证明资源隔离时才并行。

## 执行与诊断

- 使用文档化入口，不要用临时 shell 命令重造整套流程。
- 保留日志和可续跑状态。失败时先定位首个失败步骤，区分代码、环境或工具链问题，再决定是否重试；不要靠跳过步骤掩盖失败。
- 真实数据严格校验必须针对本次运行数据核实文档定义的不变量；测试套件通过不代表这些真实数据条件也成立。
- 仿真、集成测试、真实数据校验和压测属于不同证据类别，不可相互推断。
- 出现失败时先保存原始失败信息并缩小复现范围，再沿调用、状态和数据变化定位根因；修复后重跑能区分旧行为与新行为的最小验证，再按风险继续扩大范围。

## 完成前核验与报告

结束前核对实际 revision/build、命令与模式、每层是否完成/跳过、退出码和残留数据/清理状态；需要后台服务时，按进程归属确认其存活或已按预期停止，不要用宽泛匹配误杀其他会话进程。

报告上述信息、首个失败点及日志位置。明确区分已验证与未运行项目；不得把本机验收描述为 staging 或生产验证，也不得把被会话中断的任务报告为通过。
