# 套件失败定位与内容级验证方法

<a id="TST-1"></a>

## TST-1 将“CI慢”拆成可验证原因

适用于本地独跑通过而长套件失败、重试无效或容器初始化失败。先保留首个异常、测试顺序、fork/JVM、Spring context和容器实例身份，再比较独跑、同fork组合与独立fork；在事务内外分别核实fixture写入和重试每轮重新读取的状态。

检查回滚是否带走心跳/准备数据、缓存entity version是否过期、轮询是否在回调内重读以及测试Clock是否与真实超时混用。容器`<clinit>`错误本身不能证明“第23类才重复启动”；资源泄漏、OOM、端口冲突与首次启动失败是待分辨假设，需日志/进程/容器证据。

验证根因前不盲目增加重试、sleep、DirtiesContext、容器reuse或runner容量；也不把旧Wheel失败模式移植到当前Quartz实现。关闭条件是目标失败路径和受影响套件在声明环境得到验证，而非删除Disabled或弱化断言。

<a id="TST-2"></a>

## TST-2 独立预期与真实副作用

适用于重放、文件、导入/导出和批量操作。主动作走真实业务入口，JdbcTemplate用于准备与回读，不靠直接更新状态伪造流程；用独立预期对账业务行/主键、金额或控制总数、文件格式和回执，而不是只测HTTP、状态或文件存在。

断言要能抓住字段改名、重复/缺失、越租和部分提交；不从实现使用的同一集合生成全部期望。共享fixture只抽取稳定拥有权及清理责任，迁移隔离测试可有专用数据库，不能强制所有测试共用同一拓扑或按固定比例裁减E2E。
