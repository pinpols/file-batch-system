# 代码审查、可读性与验证

## 触发与边界

- 每次创建或更新 PR 前，对本次完整 diff 执行一次本 skill 的人工质量审查；用户明确要求只做指定范围时按其范围执行。
- 审查基线覆盖目标分支到当前 head 的完整变更，包括新增、修改、删除、生成物和前后端配对契约；沿调用方追踪必要的相邻代码，不把无关历史债务混成本次发现。
- 本流程审查代码语义、结构和可维护性，不是第二套 pre-commit / pre-push。先读取本轮已执行门禁的真实结果；不为重复而再次运行同一格式化、静态扫描、配置同步或编译命令。需要修复时，只补跑受影响的定向检查；风险或用户要求需要扩大时再扩展。
- 自动扫描命中只是候选，人工按业务含义判定；不得为追求清单全绿而机械拆表达式、抽方法、引入参数对象或新增门禁。
- 以 `docs/coding-conventions.md`、`docs/agent-baseline.md` 为代码风格权威。发现规则冲突时遵从更具体的调用场景和现有行为契约，不自行发明阈值。

## 审查流程

1. **先看整体**：确认 PR 目的、目标分支、完整 diff 和变更是否聚焦；先理解设计和数据/控制流，再逐行检查新增及实质改写部分。读取必要上下文和调用方，不把无关历史债务混入本 PR。
2. **按业务路径追踪**：BFS 变更优先沿 Trigger → Orchestrator → Outbox/Kafka → Worker → 状态回报/Console 追踪实际涉及的路径；核对任务/分片/实例状态、claim/lease、重试/补偿、幂等、事务和消息顺序。只追踪本次触及的链路，不要求每个 PR 重审整套系统。
3. **检查信任与数据边界**：按变更检查认证授权、tenant/ownership、RLS、SQL 参数与事务、输入输出校验、凭据/PII、异常和日志脱敏、配置与部署边界。数据库、调度、SDK、Worker、脚本等领域按需调用专项 skill。
4. **审查验证设计**：测试应证明用户可观察的结果和关键失败路径；关注并发、乱序、重复、恢复、租户边界和边界值。已有门禁通过不替代对测试语义的检查。
5. **完成可读性与代码卫生审查**：应用下方清单审查变更和调用现场；不能只看扫描器、Sonar 或 hook 的绿灯。
6. **验证疑点**：对疑似问题构造最小触发条件，沿调用链和数据流追到根因；区分根因与表面症状，不以宽泛防御代码替代因果分析。修复时优先用定向测试复现并验证；无法复现时说明替代证据。
7. **报告有证据的结论**：区分确认缺陷、明确违反项目约定、可选可读性建议和未验证假设；没有问题也要说明审查范围和验证缺口。

## 评审标准

- 目标是让本次变更不降低并尽可能改善 BFS 的整体正确性、可维护性和可理解性，不追求“完美代码”，也不因个人偏好阻塞已有清晰、有效的实现。
- 事实、可复现路径和项目规范优先于审查者偏好。格式/命名按仓库规范；规范未定义且与周边一致时，不强求统一成另一种个人风格。
- 只有会造成缺陷、安全/数据风险、重要边界违约或显著降低长期代码健康的问题才作为必须修复项。纯建议标记为“建议 / 可选”，不伪装成缺陷或阻塞项；轻微润色不应压过正确性问题。
- 每条评审意见尽量包含：位置、触发条件或具体代码路径、影响、证据，以及建议动作。避免只写“难看”“不优雅”“应该重构”；若多个方案都满足约束且风险相当，尊重作者选择。
- PR 过大或混入互不相关的改动时，优先建议按依赖关系拆分/堆叠 PR；若拆分会破坏原子性或审查上下文，则保持整体并明确审查分区。

## 可读性与代码卫生

逐项检查适用项，并查看变更上下文。结论基于阅读成本、职责和语义，不以行数或括号数量单独裁定。

### 自动门禁覆盖边界

每次审查先从 `docs/runbook/ci.md` 与 `scripts/ci/README.md` 核对当前门禁和本轮实际结果。当前 Java 自动化只覆盖部分可机械判定的规则：Spotless 格式；PMD 的明确规则（例如参数数阈值和 NCSS）；`check-java-readability.py` 的显式类型与 `@Configuration(proxyBeanMethods = false)`；依赖注入治理；以及 `PositionalArgsConventionTest` 对登记类型的长位置构造/inline Builder 调用点守护。`*ConventionTest` / `*ArchTest` 由 PR、Full、Staging 的独立 `java-governance` job 执行，标准业务测试分片会排除它们。具体范围以当前脚本和 workflow 为准，不能仅凭工具名称推断覆盖面。

以下事项目前没有通用、可靠的阻断门禁，必须由本 skill 做语义审查：任意普通方法调用的嵌套实参和复杂 `return` 表达式；复合判断是否值得提取命名 boolean；4-6 个参数是否表达一个内聚概念、以及参数对象是否只是把复杂度搬到调用点；方法职责是否混杂、某个单方法转调是无价值套壳还是有效边界；中间变量是否有业务含义；注释是否解释 WHY；类型/工厂/接口抽取是否真的减少复杂度。

这些人工项不应被括号计数、方法行数阈值或固定命名规则替代。可用 AST/静态分析生成候选清单，但除非能证明低误报并覆盖正反例，否则只作提示，不阻断提交；项目已有的精确门禁继续阻止其明确违规范围。

- **调用实参与返回表达式**：查找实参或 `return` 中嵌套多个方法调用、复杂转换、构造器/Builder 装配，导致需要逐层配对括号才能理解数据来源的写法。必要时提取有业务含义的局部变量；短小 fluent 调用、简单 DTO 映射、短工厂和声明式注册保持 inline。遵循 `docs/coding-conventions.md` §1.1、§1.4 的 Builder 长度和例外，不把所有嵌套都拆开。
- **复合判断**：检查多个 `&&` / `||` / 否定条件是否表达业务准入、状态分类或不变量。三个及以上条件共同表达一个事实时，优先评估命名局部 boolean 或小型语义谓词；简单、局部、无需业务命名的短判断不强制提取。确认提取没有改变短路、求值顺序或副作用。
- **方法参数与构造调用**：超过 3 个参数时评估是否存在更内聚的命令、查询或上下文对象；按 `docs/coding-conventions.md` §1、§1.1、§1.3 执行：Mapper 公共方法和 Service 公共接口达到 6 个参数必须封装，7 个及以上必须封装。调用方不得用超长 Builder 链把复杂度搬回现场。参数对象不能成为万能对象；构造器/DTO 等豁免按文档处理。
- **方法职责与控制流**：检查一个方法是否同时承担校验、编排、持久化、状态推进、外部调用等多个阶段；检查深层分支、重复错误处理和难以验证的长流程。需要时提取有稳定职责的私有方法/内部类型；同时识别只转调一次、没有命名语义或扩展点价值的方法壳。不要删除有明确边界职责的端口、适配器、模板钩子或兼容入口。
- **类型与契约表达**：固定 API、服务和持久化契约优先使用 DTO/record/领域类型；`Map<String, Object>` 仅保留在真实动态边界。检查 null 组合、多个 null 表示的模式、裸字符串/数字组合是否已有具名工厂、枚举或值对象可表达；只在合法状态集合清晰且能降低误用时收敛。
- **依赖注入与资源所有权**：检查构造器注入、依赖是否属于当前类、生命周期和关闭责任是否明确；审查线程、客户端、流、临时文件、锁和事务是否有清晰创建者、使用者及释放路径。不要为了“单例模式”或形式统一增加不必要的容器/工厂。
- **注释与命名**：复杂业务类及状态/恢复/补偿/并发边界的注释应说明 WHY、业务语义和不直观约束，而不是复述 WHAT；新增说明性注释遵循中文规范。检查布尔量、上下文、中间值和异常是否能表达业务角色，避免 `value`、`result`、`data` 等空泛命名。
- **重复、死代码和测试质量**：检查新增代码是否复制已有策略/工具、遗留未使用方法或仅包装的兼容层；确认测试按外部行为验证成功与失败路径，而非只验证私有实现。重构不应顺带改变事务、异常、日志上下文、幂等键、序列化或求值次数。
- **范围与一致性**：新代码与所属模块的既有模式一致吗？变更是否混入无关格式化、改名或抽象？生成文件、OpenAPI、SDK、配置、迁移、文档、运维脚本是否与行为同步？

### 可读性判断原则

- 多括号/多层调用是**定位信号**，不是自动违规。只有调用现场遮蔽业务含义、参数来源混杂或使副作用顺序难以看清时，才提取。
- 优先用局部变量解释单次调用，不要为了拆括号新增公共方法、辅助类或一层只转调的方法。
- 对建议性重构说明具体阅读成本和收益；没有可验证收益时不报“风格问题”。
- 本次 diff 没有触及某项时，标为不适用或未审，不把全仓历史扫描伪装成 PR 审查。

## 验证

- 先读仓库指导并确认适用命令、模块依赖和受支持环境；多模块 Maven 验证要包含所需上游模块（通常使用 `-am`）。
- 先检查本轮已有 hook / CI / Sonar 结果和覆盖范围，避免重复运行同一门禁；再按风险运行有针对性的静态检查和测试。只有风险或用户要求需要时才扩大到完整门禁。
- 查看命令真实退出码和进程结束状态；管道、后台任务或会话结束不能替代成功证据。被中断的任务不能报告为通过。
- 对外部依赖明确区分 mock、容器集成、本机真实服务、staging 演练和生产证据。
- 收尾前对照变更清单核实每项修改、测试和残余风险；不要仅凭日志中的局部成功信息宣布完成。
- 数据库迁移、模块/配置边界、脚本/独立 SQL 或负载测试应使用对应的专项 skill，避免在此重复专项清单。

## 发现与报告

- 先列可操作的问题并按影响严重度排序；严重度描述实际风险，不按代码行数或审查者不喜欢的风格定级。每项说明文件位置、触发条件、影响和建议的复现/验证方式。
- 将缺陷/回归、安全或数据完整性问题、明确违反项目约定、纯建议性可读性改进分开；不要把建议伪装成 bug，也不要因门禁全绿而略过人工可读性审查。
- 没有发现问题时，说明审查范围、已参考的自动门禁证据及仍未覆盖的风险。

## 借鉴来源

- [Google Engineering Practices: Code Review](https://google.github.io/eng-practices/review/)：设计、功能、复杂度、测试、命名、注释、风格和文档；以持续改善代码健康为准，不以完美主义拖延有价值的改进。
- [Microsoft Engineering Playbook: Reviewer Guidance](https://github.com/microsoft/code-with-engineering-playbook/blob/main/docs/code-reviews/process-guidance/reviewer-guidance.md)：自动化覆盖机械问题后，人工集中审业务正确性、测试正确性、可读性和可维护性，并阅读完整变更与必要上下文。
- BFS 的具体检查顺序、阈值、例外和领域边界以本仓库 `AGENTS.md`、`docs/agent-baseline.md`、`docs/coding-conventions.md` 及专项 skill 为准，不照搬外部公司的内部门禁。
