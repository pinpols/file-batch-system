# 数据库迁移安全

## 修改结构或数据前

1. 确认受影响的表、索引、约束、分区、触发器、视图、mapper、归档副本和运维 SQL。
2. 搜索所有读写路径，包括 `ON CONFLICT` 目标，以及应用对键、可空性和排序的假设。
3. 评估表规模、锁要求、回填量、复制影响和部署兼容性。
4. 在适用的每个数据库边界核实租户键和行级安全行为。

## 迁移设计

- 新旧应用版本可能并存时，优先采用可向后兼容的分阶段扩展方案。
- 限制长时间运行的工作；回填应可续跑、可观测且可安全重复。
- 修改唯一约束、主键或分区时，保持幂等语义不变或明确迁移其影响。
- 定义失败处理和恢复方案；破坏性数据变更后不要假设可以回滚。
- 结构、mapper、归档/结构镜像和运维文档彼此耦合时，应放在同一变更中审查。

## 验证

- 运行仓库提供的迁移 lint 和 schema 漂移检查。
- 条件允许时，在受支持的数据库版本及接近实际的结构/数据规模下验证 SQL。
- 检查大表或热表的查询计划和锁行为。
- 明确证据来自静态检查、本地集成、生产规模 dry-run 还是 staging 执行。

不涉及结构迁移的独立运维 SQL 或 shell/Python 中的 SQL，改用 `script-sql-governance`。
