# ADR-047：Workflow 调度归属与每日业务义务

- 决策日期：2026-10-14。
- 状态：Superseded；由 [ADR-048](./ADR-048-workflow-fresh-database-cutover.md)取代。下文保留 `2026-10-14.1` 的历史决策；旧系统兼容、旧库升级和混合版本验收已退出当前范围。
- 契约版本：`2026-10-14.1`。本 ADR 归并两个活跃方案中已同步的共同约束，不提升已有局部实现的完成状态。
- 实施入口：[隔离整合计划](../../plans/workflow-daily-integration-plan-2026-10-14.md)。

## 背景

Workflow 改造将顶层日程及运行归属迁到 Workflow；每日连续性改造引入定时 occurrence、输入预期和结算覆盖证明。两个分支独立实现时，共享启动载荷、定时身份、业务日以及空日结算容易使用不同事实来源。合并代码、编译或各自测试通过均不能消除这类所有权冲突。

保留 [ADR-002 的事务 Outbox](./ADR-002-transactional-outbox.md)、[ADR-010 的异步触发](./ADR-010-trigger-async-decoupling.md)、[ADR-017 的结果版本](./ADR-017-result-version-model.md)和 [ADR-043 的依赖等待](./ADR-043-dependency-aware-fire.md)边界。本决策明确新模型的共同约束；历史运行继续按其冻结版本解释。

## 决策：对象职责与唯一写入责任

| 对象 | 目标职责 | 写入与边界 |
|---|---|---|
| Workflow Definition / Run | 顶层调度目标、编排图、整体运行和冻结上下文 | Workflow 配置是新顶层日程的来源；Trigger 受理触发，Orchestrator 创建与推进 Run |
| Job Definition / Instance | 可复用执行配置，以及某个节点的具体执行 | Job 不维护第二份顶层日程；Job 页运行经受管 Workflow；节点执行不递归启动该 Job 的受管 Workflow |
| 系统 Pipeline | 按执行类型确定标准阶段与兼容版本 | 系统目录维护阶段模板；Job 保留类型化业务参数；Worker 按冻结版本执行 |
| 定时 occurrence | 一次原计划 fire 的身份、日期、计划版本及处置证据 | Trigger 使用 Quartz 计算并物化；Orchestrator 消费其关联结果，不另算 cron |
| 文件/事件预期项 | 到达前可声明的输入义务及匹配证据 | 规则由既有配置入口维护，Orchestrator 开日按冻结规则生成；文件/事件适配器仅经受支持入口提交到达与关联证据 |
| BatchDay | 某业务日义务履行、在途工作和结算事实 | Orchestrator 依据完整预期及运行结果结算；不从零实例推断无工作 |
| 运行快照 | 图、有效 Job 参数、Pipeline 版本、日期解析及依赖证据 | Orchestrator 冻结本次运行所需信息；恢复复用；不扩大为全平台资源快照 |

沿用 `DB → Outbox → Kafka → CLAIM → EXECUTE → REPORT`、租户隔离、数据库唯一约束/CAS 和 Orchestrator 唯一运行状态主机。下列语义优先复用现有表与端口；不据此预建通用调度框架或新的消息主链。

## 决策：必须同时满足的七项规则

1. **ALIGN-1：统一运行根。** 新顶层运行均为 `workflow_run → workflow_node_run → job_instance`，单作业与组合流程使用同一节点执行路径。Job Instance 不兼任 Workflow 父计数容器；历史 wrapper、根 Job 复用和父虚拟任务仅按明确的旧模型恢复。兼容退出须列出旧消息/活跃运行范围、对账和排空条件，不能只因新路径上线就移除历史解释能力。
2. **ALIGN-2：触发时间与数据日期分开。** Workflow 日程决定计划触发时间；接纳触发时固定原 fire/事件时间、`bizDate`、数据区间及可重现日期解析的日历版本或规则快照。子 Job 默认继承流程业务日，确需跨日时由节点/依赖边显式声明日期映射和使用的日历。延期释放、重试、catch-up/replay 不用执行当天重算；旧请求沿用原日期与兼容策略。日历的“允许触发”与“有业务义务”分别判定。批次窗口属于节点资源准入覆盖，不迁成 Workflow 全局日程；运行冻结窗口引用/覆盖，平台紧急管控等实时策略另按现有契约执行。
3. **ALIGN-3：触发机会与执行尝试分开。** 当前每 Workflow 一套日程时，定时身份采用 `tenant_id + workflow_definition_id + original_scheduled_fire_time`（epoch millis），不以可变 Job/Workflow 编码作最终身份。调度版本是冻结属性，不因版本递增使同一计划时刻获得第二次运行资格；一日多次 fire 分别记账。Quartz 重扫、消息重投、readiness 延期和同一请求重试复用原 occurrence；用户明确重新处理数据时创建带来源关系的新运行/请求，不复活旧终态。事件身份包含租户、生产来源与稳定事件 ID；文件身份使用已持久化的到达组身份及明确业务日/批次，通知、扫描和 sensor 关联同一来源。配置替换只能对尚未发生的旧计划作可审计 supersede；已发生、待审批、在途及终态记录保持原关联。旧 Job fire key 与新 Workflow key 必须有可追溯映射，切换前后仅一个生效派发入口。
4. **ALIGN-4：按义务结算。** 定时预期来自权威 Workflow 日程与连续覆盖证据；文件/事件预期来自到达前声明的业务规则。BatchDay 保存或引用本次预期生成所用规则版本/快照和覆盖证据，不能由当天已运行 Job 反推完整清单，也不能将所有 DAG 节点一律列为必跑。条件未选中的分支须有跳过原因，必需业务结果则须显式声明义务。区分待履行、已履行、按规则豁免和失败待处理的业务含义，复用或精确扩展现有状态。输入已到达或请求已 LAUNCHED 只结束对应到达/触发等待，不能直接证明业务结果已履行；关联运行、依赖等待和结果义务继续参与结算。自动空日结算须同时证明预期覆盖完整、无待履行义务、无在途工作，并保持现有 CUTOFF/零实例前置条件。事件截止、迟到和缺失处置必须显式，未知不自动判空；人工豁免/结算记录原因、权限、覆盖缺口和受影响义务。只为 `workflow.enabled=true` 的 Workflow 创建未来文件组/事件预期；禁用 Workflow 后停止新增预期，但不删除已生成义务。`schedule_enabled=false` 只暂停定时触发，不取消文件/事件输入义务。
5. **ALIGN-5：控制依赖与数据依赖分开。** DAG 边表达执行顺序及成功/失败分支；跨运行数据依赖表达上游业务日、分区、结果条件与版本。两者组合放行时分别记录阻塞原因；Trigger readiness 只作快速预检，Orchestrator 按同一契约最终裁决与持久化等待。等待尚未放行时按声明策略解析候选版本；放行后冻结选定版本，平台可控读取路径必须实际按该版本读取，缺失时失败而非静默换成最新。仅记录 gate 观察版本、尚未固定实际读取的 Worker/SDK/外部处理器明确标记“消费版本未追踪”。上游修订不隐式重跑已启动下游；需要更新消费时显式 replay 并保留来源。
6. **ALIGN-6：固定阶段不吞掉业务配置。** 系统 Pipeline 只固化类型能够决定的标准阶段、顺序及平台执行契约。PROCESS 插件/SQL/业务参数、已有且实际生效的重试/超时配置逐项迁移并冻结；未知或冲突字段先阻断转换，不忽略或凭字段存在赋予新语义。运行固定 Pipeline code/version 和有效 Job 参数。升级前明确 Worker 版本支持范围；旧运行须由兼容执行器完成/恢复或按受控策略排空，不按最新模板解释旧快照。
7. **ALIGN-7：先对齐共享契约，再逐片整合。** 两分支先统一 Launch/Trigger 字段、互斥目标、occurrence/预期项关联、日期与状态语义，再安排 Flyway 顺序、API/OpenAPI/前端和配置包兼容。未发布迁移按最终集成序列消除撞号；已发布迁移不得改写。不直接以 Git 无冲突作为语义整合成功，也不等两个分支各自全部完成后才核对接口。尽早在隔离整合分支完成最小统一链，再继续后续切片；进入 main/发布仍须相应验收与用户授权。

## 联合验收与推进顺序

| 验收项 | 必须观察到的结果 | 最小证据 |
|---|---|---|
| A1 同一业务日修改日程、重复 fire/消息、双实例恢复 | 已发生 occurrence 身份不变；一个合法根运行；重复投递不新增节点尝试；明确 reprocess 才新增有来源运行 | 真实 PostgreSQL/Kafka 并发及 Quartz 回调 |
| A2 跨午夜、节假日/DST、不同日历节点、readiness 延迟后重启 | 原业务日、区间、日历依据与节点映射保持；不以恢复当天重算 | 日期边界测试与真实持久化恢复 |
| A3 条件分支、事件未到、已到但未运行、运行失败 | 未选分支不误报漏跑；未知覆盖阻止自动判空；输入满足不掩盖在途/失败义务；人工处置可审计 | 真实 PostgreSQL 状态/事务集成与 Console 旅程 |
| A4 gate 通过后上游 promote、下游延迟执行/重试 | 支持 pinning 的读取仍使用选定版本；不支持的明确为未追踪；显式 replay 保留新旧来源 | 真实业务读取与版本竞争验证 |
| A5 单 Job、组合 Workflow、legacy wrapper 与旧 Pipeline 消息 | 新运行只有统一根/节点归属；旧运行按旧模型恢复；计数、配额、终态与业务副作用不重复 | Worker/Orchestrator 故障恢复与混合版本验证 |
| A6 两分支迁移合并及配置包导入 | 全新库与存量升级均成功；旧 Job occurrence/请求/预期到 Workflow 可对账；热冷历史可解释；冲突无部分写入 | 真实 PostgreSQL 迁移、Excel/JSON Apply 与回退演练 |

推进顺序：共同契约与字段/迁移对照 → 最小统一 Workflow/occurrence/节点运行链 → BatchDay 业务义务与版本消费 → 联合恢复验收 → 兼容入口退役。各分支可以继续不冲突的切片；涉及上述边界的代码和迁移必须先按共同契约复核。A1–A6 是联合完成条件，已有定向测试只证明原场景，不能自动覆盖这些组合场景；通过记录须固定整合 SHA、命令、数据/环境及结果。


## 理由与后果

- Workflow 是日程的唯一权威来源，Job 作为可复用执行配置，避免一个业务触发被两套调度器接纳。
- occurrence 记录计划机会，运行和重试记录执行；分开保存才能同时解释漏触发、重复投递与显式重新处理。
- 空日结算需要完整覆盖和业务义务证据。未知状态保持待处理，会增加人工治理需求，但能避免错误结算。
- 日期、配置和依赖版本的冻结增加持久化与兼容成本；需保留历史映射、迁移对账、监控和退出条件。
- 固定 Pipeline 只能覆盖类型决定的阶段；业务参数和受支持版本仍须独立维护，不能因简化配置而丢失。

## 已排除的替代方案

- 同时以 Job 和 Workflow 日程为权威：存在重触发和两个覆盖清单不一致的问题。
- 用 Job 实例数量或触发请求已受理证明业务日完成：缺少尚未到达、尚未启动和失败义务的证据。
- 按最新配置恢复旧运行：改变原业务日、执行阶段或消费版本，无法解释原结果。
- 直接删除 Pipeline 历史或旧 wrapper 路径：已有消息、运行、归档和重试仍需要旧语义。
