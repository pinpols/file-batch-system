# Dispatch 密钥版本运行时语义

## 决策

- 新建作业实例时，平台解析其 Dispatch 渠道引用，并把 `secretRef + secretVersionId + versionNo` 写入实例参数快照。普通 Dispatch 使用作业渠道，文件束 Dispatch 按各分区的目标渠道分别固定；密钥明文不进入作业快照、Kafka/outbox 或日志。
- 文件束 Dispatch 的渠道集合与分区展开使用同一份有效文件清单；任一实际目标渠道缺失时拒绝创建该作业实例，不丢弃其他渠道快照并回退读取最新配置。业务元数据中的同名字段不作为渠道。
- 普通 Dispatch 按调度和 Worker 的字段优先级确定顶层明确目标；该渠道不存在时拒绝创建作业实例。识别到多个渠道时，已捕获的渠道快照会保留；任务若指定了不在这份非空快照中的渠道，Worker 拒绝回退到最新配置。没有顶层明确目标且未捕获到任何渠道的请求仍沿用现有处理，不能仅凭这一规则证明其渠道配置已冻结。
- 普通 Dispatch 有明确目标时，递归识别到的其他渠道若没有可用密钥版本，不阻断明确目标，也不写入该候选的密钥绑定；任务实际使用未绑定的凭据渠道时仍由 Worker 失败关闭。文件束的每个实际目标和没有明确目标的普通请求保留严格校验。
- 整 Workflow Replay 对有明确目标的普通 Dispatch，原配置策略使用来源中已冻结的候选渠道，最新配置策略固定能捕获的候选渠道；未捕获的其他候选不阻断重放。非目标候选已停用，或引用密钥但没有可用绑定时，不写入重放快照；停用候选已有绑定时先校验再一并移除。实际目标必须启用且有完整配置和所需密钥绑定，已有绑定仍须通过身份和版本校验。审批快照不能包含请求未识别的渠道，后续启动只使用已批准快照。无明确目标时仍要求候选集合全部固定。
- WorkflowRun 冻结图和运行配置；实际到达 JOB 节点时，在该节点 JobInstance 创建事务中解析并固定 Dispatch 密钥版本。不创建 TASK/FILE_STEP 虚拟父实例，不信任调用方传入的内部绑定字段。
- 排队、执行和重试都使用同一个固定版本；轮换只影响之后创建的实例。不得在执行或重试时静默切换到当前版本。
- Console 轮换入口先沿用文本清洗规则（NFKC 及首尾空白清理）确定存储引用，再在同一事务中以该引用加版本锁、查询下一版本、降级旧当前版本、写入新版本和审计。空白或全角别名归属同一租户下的同一版本序列；DRAFT 递增版本但保留已有当前版本，PUBLISHED/GRAY 才更新当前版本。原请求对象不改写，查询与 Worker 固定快照仍按各自精确引用契约处理。
- 每次外部投递前，Dispatch Worker 按租户和固定版本 ID 读取受保护载荷，并校验版本仍在有效期且未撤销。撤销优先于实例快照，阻断尚未发出的请求及后续自动重试。
- 只有成功进入投递调用所需的凭据会短暂注入运行态渠道配置；投递与可选回读结束后立即移除。
- 未解析、引用不匹配、解密失败、字段不允许、版本撤销或过期均 fail-closed，不回退到明文配置或最新版本。

## 故障与恢复边界

- 撤销前已经发出的网络请求无法召回。若远端结果不确定，系统不因密钥问题自动重新发送；运维应先核对下游结果，再决定是否以新实例补发。
- 正常轮换不撤销旧版本。旧版本按 `effective_to_at` 或明确撤销策略失效，避免排队实例因轮换被无声改写。
- ADR-048 的切换使用全新数据库和隔离消息命名空间，不接旧任务队列。新系统中缺失版本快照的异常任务仍失败关闭，不擅自读取最新版本；外部结果不明时先核对证据再恢复。
- 配置写入、审计和撤销状态由 Console/配置域负责；实例快照由 Orchestrator 在 launch 事务中生成；Worker 只按快照读取并执行，不拥有密钥版本选择权。
- 不扩展到平台资源快照/恢复、租户路由重构或容量公平性调度；这些属于独立需求。

## 验收范围

单测覆盖 launch 固定版本、缺失版本拒绝、Worker 精确版本读取、撤销拒绝、凭据清理和不可重试错误；真实 PostgreSQL 集成测试覆盖迁移约束及租户/版本/撤销/有效期过滤。CI 与生产环境验证仍以各自运行结果为准。

2026-10-27 的定向补验通过真实 HTTP 与 PostgreSQL 验证空白/全角别名轮换、草稿到灰度及租户隔离，共 4 项集成用例；另有 5 项受影响单测验证轮换身份/顺序、版本状态、JSON 拒绝和旧载荷对象加密入口。集成采用本地测试安全旁路，不作为认证、生产负载或多节点验收证据。
