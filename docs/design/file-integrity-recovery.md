# 文件完整性与故障恢复方案

## 目标与适用范围

本文定义对象存储入站、到达组、导入校验和 NAS/SFTP/OSS 出站交接的文件完整性边界。目标是让系统可以区分“对象存在”“对象写完”“字节校验通过”和“业务处理成功”，并在进程中断、对象损坏或重复扫描后安全恢复。

本方案不承诺存储介质损坏后的底层修复，也不以数据库事务隔离替代对象存储一致性。生产数据恢复仍依赖对象存储版本/备份能力和业务侧可重放来源。

## 状态语义

文件生命周期分为四个独立事实：

1. **发现**：对象存储列举到文件。
2. **发布完成**：稳定窗口通过，且所需完成标记/manifest 已发布。
3. **完整性验证**：实际对象字节数和摘要与 manifest 一致。
4. **业务完成**：解析、规则校验、入库或分发完成。

`file_record` 的 checksum 字段是“期望校验值”，不单独代表第 3 项已完成。到达组开启 `require-verified` 时只接受 `metadata.integrityState=VERIFIED` 的成员。

## 入站协议与处理

### MANIFEST 模式

- 数据对象先完整发布，`.chk` manifest 最后发布；对象存储使用完整对象 PUT，文件系统使用临时文件、flush/force 和同文件系统原子 rename。
- manifest 必须声明 `schemaVersion=file-sidecar-manifest-v1`、同目录 `fileName`、`sizeBytes`、`checksumType=SHA-256`（兼容拼写 `SHA256`）和 64 位十六进制 `checksumValue`。入站不再接受 MD5 sidecar：MD5 不能抵御恶意碰撞，且不能作为 `integrityState=VERIFIED` 的依据。使用 MD5 的上游必须先切换为 SHA-256，否则文件会被拒绝登记，到达组可能持续等待。默认 `checksumScope=RAW_OBJECT`；其他 scope 不允许被误当作原始对象校验。
- scanner 先检查标记存在、数据对象稳定、manifest 格式/文件名/长度有效，再对对象流式计算 SHA-256。流式计数必须等于扫描快照长度，摘要必须常量时间/安全比较通过后，才写入带 `integrityState=VERIFIED` 的记录。
- 同一摘要仍在导入 preprocess 阶段复核，作为存储到处理之间的第二道检查。摘要不匹配时不得 launch/import；已登记对象的 preprocess 校验失败仍进入既有失败状态，不自动把失败任务标记成功。
- 校验失败不创建可触发的已验证记录。scanner 记录脱敏错误摘要并继续重试；对象被上游修复/重新发布后，后续扫描可成功登记。重试日志需限频，不能输出内容、凭据或绝对路径。

### MARKER 模式与兼容

- `MARKER` 只代表上游声明传输结束，不提供字节完整性保证。保留现有配置和行为，不将空 marker 宣称为 checksum 验证。
- `MANIFEST` 协议缺字段、MD5/未知算法或不支持的 checksum scope 按验证失败处理，不静默降级为 marker。上游必须在启用 MANIFEST 前发布 SHA-256 sidecar，并确认其校验值覆盖原始对象字节。
- 对旧 `file_record`，只有有可信校验来源且确认已完成实际摘要比较时，才能回填 `integrityState=VERIFIED`；不能仅依据 `checksum_type != NONE` 回填。

## 到达组与数据库并发

- `requiredFileSet` 定义本组预期文件集合，是稳定集合的业务来源；单次对象存储 list 不是跨请求快照。
- `ALL_OF` 的每个必需成员均需存在且完整性状态为 `VERIFIED` 才能触发。校验失败留在等待/人工处理路径，并按既有超时策略收敛。
- 到达组触发仍须由数据库中的幂等请求键、唯一约束和状态 CAS 防止多个扫描周期重复提交。目录新增对象属于存储发现问题；数据库幻读属于事务查询集合问题，两者分别治理。
- manifest 中的业务日期、批次号、租户和文件组若同时由批次清单/路径声明，应校验一致，避免将合法 checksum 文件归入错误业务组。

## 出站发布与半写防护

- NAS：数据写入唯一临时名，流式计算长度与 SHA-256，成功后原子 rename 正式数据文件；随后临时写入并发布 manifest。失败清理临时文件。
- SFTP：上传临时远端名并 rename 数据文件，再上传并 rename manifest；服务端不支持可靠 rename 时不得宣称具备原子发布，需要渠道配置拒绝此模式或明确退化策略。
- OSS/S3：完整对象 PUT 成功后再 PUT manifest；manifest 是下游消费信号。若采用 multipart，只有完成 multipart 后才发布 manifest。
- 目标消费者只在 manifest 存在且本地复算长度/摘要成功后读取。远端写成功但 worker 在保存 dispatch 成功状态前崩溃时，重试需使用稳定目标键/幂等请求键；覆盖发布遵循“数据先、manifest 后”。
- `.tmp-*` 仅可按配置保留期清理，清理前检查对应活动任务/租约；不能按短固定 TTL 删除仍在进行的大文件上传。

## 文件系统原子性与恢复

- 同目录临时文件、完整写入、长度校验、`FileChannel.force(true)`、同文件系统 `ATOMIC_MOVE` 是正式发布路径。
- `ATOMIC_MOVE` 不支持时默认拒绝发布并清理临时文件；普通 `REPLACE_EXISTING` 不能作为等价 fallback，因为扫描者可能观察到替换窗口。若运营选择显式降级，必须启用完成标记协议、限制消费者，并在启动检查/健康状态中暴露降级事实。
- 崩溃遗留临时文件不自动提升为正式对象。清理由运维任务按年龄、活跃任务引用和租约确认后执行；正式对象校验失败则从可信上游重传或从存储版本/备份恢复。
- 读已发布文件时应视作不可变对象。更新同 key 必须通过完整临时对象替换，并使用版本/ETag 或业务版本避免读写覆盖竞态。

## 恢复矩阵

| 故障 | 系统行为 | 恢复动作 |
|---|---|---|
| 数据文件先到，manifest 未到 | 不登记/不触发 | 等待上游发布 manifest；超时进入现有人工/超时处理 |
| manifest 截断、字段非法、长度或摘要不匹配 | 不置 VERIFIED，不触发导入/到达组 | 修复或重新发布源文件和 manifest，再扫描；保留失败证据 |
| worker 在读取/处理时崩溃 | 由租约/任务重试恢复，重新校验对象 | 幂等重试；不跳过摘要校验 |
| 本地/NAS 临时文件遗留 | 不视为正式对象 | 校验无活跃任务后清理；必要时由源端重传 |
| 出站数据已发布、manifest 未发布 | 下游不消费；dispatch 可重试补发 manifest | 以稳定目标键核对数据并重新生成 manifest |
| 数据/manifest 均发布、数据库状态未提交 | 对端可能已具备消费信号 | 重试前比对目标 checksum 和请求幂等键，避免重复副作用 |
| 正式对象 checksum 后续不匹配 | 隔离，不继续处理 | 从对象版本/备份或上游重传恢复；调查存储/传输链路 |

## 观测与运维

- 日志和指标至少区分等待 marker、manifest 解析失败、长度不符、摘要不符、存储读取失败、发布失败和遗留临时对象；日志只包含脱敏对象标识、租户安全键和 trace id。
- 告警需区分持续待 manifest、完整性失败率、对象存储错误率、临时对象积压和到达组超时。
- 运行手册需提供按 file id/trace id 查证、重新扫描、重新导入/分发、人工确认和从备份恢复的步骤，并记录操作审计。

## 分阶段落地与验收

### 阶段一：入站校验闭环

实施 MANIFEST 必填字段/文件名/scope 校验、scanner 原始对象流式 SHA-256 校验、长度二次确认、`integrityState` 持久化和到达组 VERIFIED 判定。保持 MARKER 兼容，但明确其不提供 checksum 保证。

验收：缺 marker、非法 manifest、长度错误、摘要错误均不触发；有效 manifest 注册 VERIFIED；到达组要求 VERIFIED 时拒绝仅有 checksum 字段的旧记录；导入 preprocess 仍可拦截登记后对象被替换/损坏的情况。

### 阶段二：发布原子性与恢复运维

移除普通 move 的隐式原子性降级；增加可观测启动/健康信号和安全临时文件清理运维流程。明确不同 NAS/NFS/SFTP provider 的 rename 支持边界。

验收：原子 move 失败不暴露正式文件；临时文件清理不会命中活跃任务；降级配置可发现且有明确风险说明。

### 阶段三：运行环境验证

对实际使用的本地文件系统/NAS、S3 兼容服务和 SFTP 服务执行并发读写、进程中断、rename、read-after-write、重复投递及故障恢复演练。记录服务版本、挂载选项、负载、结果和未覆盖项。代码单测/集成测试通过不能替代此阶段。

## 当前基线和限制

仓库已有对象存储抽象、FS 临时文件写入、入站稳定窗口/manifest 校验、导入 preprocess 摘要复核、出站 NAS/SFTP/OSS manifest。阶段一已将入站原始字节摘要验证前移到登记前，到达组 `require-verified` 改为要求 `integrityState=VERIFIED`；FS put/copy 与 NAS dispatch 不支持原子 move 时现已失败关闭。剩余待完成项包括 SFTP 替换发布和旧 manifest 撤销顺序、临时文件安全回收运维流程，以及 S3 兼容性、NAS/NFS 和外部 SFTP 的目标环境验证。
