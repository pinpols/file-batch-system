## 容量画像结果

### 1w

- 入口：10000/10000 成功。
- 200 RPS 下 p95 为 5831ms，Gatling 的 500ms 延迟断言未通过。
- 结论：可以收敛，但不能承诺 200 RPS 的低延迟 SLA。

### 10w

- 入口：100000/100000 HTTP 请求无 KO。
- 运行窗口内形成约 35696 个实例，其中约 7 个仍为非终态；600 秒终态等待超时。
- 任务结果：约 11229 SUCCESS、约 24460 业务拒绝/失败；Kafka 快照未显示持续增长的 lag。
- 结论：当前本地 profile 的准入/背压上限已被测出，10w 不通过容量承诺门槛；不能把入口 HTTP 0 KO 当作 10w 业务成功。

### 多租户公平性

- ta p95 123.193s，tb p95 113.666s，tc p95 130.893s。
- 三租户最终均全成功，未见饿死或跨租户串数据。
- 结论：正确性和最终公平通过，但高压下延迟较高，仍需生产容量参数和更长窗口确认。

### 压测清理复验

- 首轮全量 sim 暴露了压测清理脚本将租户固定为 `default-tenant` 的测试缺陷，导致公平性 `ta/tb/tc` 残留并污染后续 Stage 21。
- 已改为以每轮唯一 `run_id` 为边界，移除租户硬编码；清理前等待实例行数稳定，锁冲突最多重试 6 次，并对残留返回非零。
- 修复后 reset 本地运行态、重新装配 Docker 基础环境和租户 fixture，再跑完整 sim，所有标准阶段通过；这次结果不包含上一轮残留。

## Soak 结果

本地短 soak 在 2 分钟、2 RPS 运行时被监控器主动终止：磁盘使用率 97%，超过 90% 保护阈值。该行为符合安全设计，不能通过调高阈值绕过。

因此本轮只证明了：

- 磁盘保护退出条件生效。
- 报告生成链路生效。
- 24h soak 尚未完成。

要完成 30 分钟/24 小时 soak，需先为 Docker/宿主机释放至少 30GB 可用空间，再用 `run-worker-soak-tests.sh` 运行；不得在当前 97% 磁盘占用下强行运行。

## CI 维护

`.github` 中的 `actions/setup-java` 已升级到 v5，`actions/cache` 已升级到 v5。升级后的完整门禁由主干 run `32425735857` 验证通过。

容量脚本现在会保留被测命令的退出码：默认 `CAPACITY_STRICT=0` 用于容量画像（低延迟断言失败仍生成报告），发布验收或 CI 应使用
`CAPACITY_STRICT=1` 将 10w 低延迟断言转为硬失败；公平性脚本失败始终使画像失败。清理脚本对 PostgreSQL 锁冲突最多重试 4 次，避免压测残留掩盖真实结果。

- 未发现新的生产 `TODO/FIXME` 事项；扫描命中的 `XXX` 主要是日期格式、临时文件模板和测试 URL，占位符治理不应误伤这些合法用法。

## 当前边界

- 10w 本地画像是容量上限证据，不是生产容量承诺。
- 真实云 S3、真实 SFTP/NAS、跨节点 Kafka/PG 自动故障切换仍需同构 staging 演练。
- 文件束导入阶段默认保持 opt-in，本轮验证了入口守护未污染标准 sim；显式 `RUN_BUNDLE_SIM=1` 仍应单独在兼容 worker 镜像环境执行。
- 长类和动态 Map 仍应按业务边界渐进收敛；本轮不做无行为变化保证不足的大规模重构。
