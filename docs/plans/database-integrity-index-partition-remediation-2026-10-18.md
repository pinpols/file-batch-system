# 数据完整性、索引与分区治理整改方案

> 状态：主线实施方案，整改与验收待推进。方案依据 feature 分支审查中发现的高风险项整理；主线接手后须合并逐表证据并重新核对当前实际 PostgreSQL catalog。本方案不表示迁移已执行或验收通过。
>
> 范围：数据库外键/数据引用、应用层引用守护、索引、分区、RLS 与归档生命周期。先处理租户隔离和可证明的数据丢失风险，再处理清理/恢复语义，最后按真实查询证据优化索引与分区维护。
>
> 部署边界：按用户已确定的全新数据库部署，不承担旧系统兼容与历史库转换。本方案由主线与整合分支共同采用；现有逐表专题保留证据及原任务编号，本方案统一阶段顺序和验收要求，不重复计算完成项。

## 1. 优先级与阶段门

| 阶段 | 优先级 | 目标 | 进入下一阶段的条件 |
|---|---|---|---|
| A. 隔离与数据安全 | P0 | 修复分区叶子直连的 RLS 边界；修复可证明的归档数据遗漏；核实应用角色属性 | 普通应用等价角色父表/叶子跨租户负例通过；冷热记录逐字段对账；复制失败时热数据保留 |
| B. 生命周期与引用完整性 | P1 | 闭环 PROCESS staging 清理、归档/重放引用、跨租户外键、应用守护一致性及迁移顺序 | 在途、长任务、失败重试、等待恢复和历史取证不因清理丢失；约束预检无未解释孤儿；应用与数据库对同一引用的身份、空值和生命周期语义一致 |
| C. 查询与索引 | P2 | 修复已证实的查询谓词/索引漂移，按真实计划优化热点 | 代表性查询计划、延迟、锁和写放大满足明确验收标准 |
| D. 扩展与冗余治理 | P3 | 评估分区扩展、父索引继承、重复/覆盖索引和维护成本 | staging/生产统计及计划证明收益；唯一性、FK、ON CONFLICT、稳定排序语义不退化 |

不得把 P0/P1 降为“仅测试”；不得仅凭低 `idx_scan`、结构相似或本地空库数据执行 DROP/重建。

## 2. P0：租户隔离与归档数据安全

### 2.1 分区叶子 RLS

- 从实际数据库 catalog 逐一盘点含 `tenant_id` 的 `biz` 表及 `batch.process_staging` 父表、所有叶子分区的 `relrowsecurity`、`relforcerowsecurity`、policy、owner、grant，以及应用角色 `rolsuper`/`rolbypassrls` 属性。
- 父表策略不能替代叶子表直接访问保护。迁移、strict 切换和回滚都应覆盖已有叶子；运行时新建分区须在同一事务内启用并强制 strict RLS 后提交。
- RLS 闭世界守卫扫描叶子并报告缺策略；不得只扫描普通表，也不得以特权测试账号作为隔离证据。
- 验收使用 `NOSUPERUSER NOBYPASSRLS` 的应用等价角色，直接查询叶子验证跨租户读写隔离，同时覆盖父表路径、strict/rollback、新分区及守卫负例。

### 2.2 归档完整性与引用保全

- 对每条归档路径核对热表列、归档列、INSERT/SELECT 对齐、冲突处理、删除顺序、事务边界及冷查询/恢复入口。
- 已识别候选缺口：独立 Workflow 节点归档需保留 `workflow_node_run.job_instance_id`；删除热节点前应验证冷表中的关联及完整运行树。同步比较 SuccessInstance 归档路径，不能只修一条入口。
- 检查 `pipeline_progress` 等续跑/checkpoint 数据是否存在生产搬运和恢复路径；只有冷表 DDL 不代表归档实现。父运行记录删除时不能留下无法恢复的热孤儿，也不能用级联删除丢掉检查点。
- 集成验收覆盖归档后热数据删除、冷热字段快照一致、关联回查、重试幂等，以及复制失败时热数据保留。

## 3. P1：外键、清理与跨日生命周期

### 3.1 外键逐表裁定

- 依据真实 catalog 逐表、逐约束分类：应新增、应升级为 `(tenant_id,id)` 复合关系、保留现状、无需 FK（历史快照/多态身份/跨库弱关联/独立生命周期）及已有替代校验。
- 全新空库按父端复合唯一键、子表及约束依赖顺序初始化，完成 migrate/validate、重复初始化及种子数据检查；不为旧数据兼容降低新库约束。上线后新模型数据库的正常升级另评存量预检、锁、失败恢复及分批验证；`NOT VALID → VALIDATE` 仅在目标 PostgreSQL 版本和表类型支持时采用，不机械套用所有分区场景。
- CASCADE/SET NULL 必须证明不会跨租户修改子行或删除审计、通知、恢复证据；可空复合关系逐列明确语义，不能让部分 NULL 绕过必填引用，也不能将租户身份一起清空。
- 应用层守护与实际约束逐条对齐，具体按 §3.2；原生 FK、RLS、应用业务校验和历史弱引用分别记录保证范围。

### 3.2 应用层引用守护与数据库约束对齐

本节属于 DBSAFE-3 的实现与验收条件；涉及当前租户隔离、运行血缘或归档数据安全的缺口随 P0 一并处理。其余按 P1 推进，不因补了文档或已有 Service 校验而标记完成。

V303/V304 的日历引用是此要求的具体例子：Console 先以当前租户解析 `calendar_id`，随后数据库用 `(tenant_id,calendar_id)` 复合FK守住相同身份；预检不能按 ID 查询后丢弃租户条件，数据库也不能只约束裸 ID。V304 的组关系目前没有生产应用写入口，所以由数据库复合FK保护直接SQL；将来新增入口须沿用 `(tenant_id,group_code)` 和代表日历三列身份。V305 的分区 JobInstance 引用则不能表达成普通复合FK：应用/Mapper 仍在持久化同一 Workflow 节点引用，数据库以子写 `FOR KEY SHARE` 与父删/改键 trigger 构成双向并发围栏；租户清理和归档须按子先父顺序。若出现并发错配，数据库拒绝必须回滚写入并映射为稳定冲突响应。

Outbox 的应用守护和数据库约束已在 V306 对齐为同一引用身份：父表唯一键为 `(tenant_id,id,created_at)`；两张热子表新增 `outbox_event_created_at`，以 `(tenant_id,outbox_event_id,outbox_event_created_at)` 建立 `NO ACTION` 原生复合 FK。Kafka 投递回调与 retry 写入通过同一身份锁定热父行；归档器锁候选父行后在同事务迁移父子记录，归档已提交后到达的子记录按同一身份写入冷子表，冷热父行都不存在时以完整性错误失败。清理 SQL 也按同一身份先删 delivery/retry 子行、再删父事件。V306 的真实 PostgreSQL 迁移、直接 SQL 错租户/缺父/父删除负例及两个独立事务的归档竞争已有局部验证；31项合并回归加分区约束目录断言1项，共32个不同用例通过；这不关闭 REF-02，完整运行树/分区淘汰、所有旁路、故障恢复和联合验收仍开放。

Catch-up audit 的应用守护和数据库约束也须按 occurrence 的完整身份一致。`ScheduledOccurrenceRecorder.acceptRejectedOccurrence` 先用 `(tenant_id, workflow_definition_id, scheduled_fire_time, biz_date)` 与 `CLOSED_DAY_REJECTED`/空 request 条件更新；新 request ID 随后与相同四列写入 audit。V307 将 occurrence 的候选键扩为上述四列加 `request_id`，audit 以相同五列建立 `NO ACTION` 复合 FK。真实 PostgreSQL 负例拒绝错 request 和错 bizDate，合法 catch-up 主链保留，定向回归28/28通过。此约束仅依赖全新数据库在应用流量和业务种子之前迁移；在线升级尚无设计与证据。

批量日重放的 `BatchDayReplayService.submit` 同样按 `(tenant_id,session_id)` 核对持久 session 与每个 entry 的租户，错配在 Mapper 写入前失败；V308 的相同两列 `NO ACTION` 复合 FK 防止直连 SQL 和并发父子错配。真实 PostgreSQL 直写负例证明旧单列 FK 会接受跨租户 entry，升级后拒绝；现有 dry-run 与 OUTPUTS_ONLY 重放主链仍通过，相关单测/集成共38/38。全新数据库迁移在运行时数据之前执行，在线升级仍未设计或验证。

预览 token 的可空 `session_id` 也按 `(tenant_id,session_id)` 对齐。`BatchDayReplayPreviewTokenMapper.linkSession` 以同租户 session `EXISTS` 为更新条件，更新 0 行由 submit 事务失败关闭；V309 另加相同身份的 `MATCH SIMPLE`、`NO ACTION` 复合 FK，令未链接 NULL 合法并阻止引用 session 被提前删除。过期 token 由有界 `deleteExpired` 先清理；4-day SIM 清理 SQL 显式包含 token。真实 PostgreSQL 数据库和应用入口及 token 生命周期、有效 replay 回归42/42通过。完整 archive/recovery 语义未闭环。

`batch_day_waiting_launch` 的 V310 将 `(tenant_id,request_id)` 绑定到 `trigger_request(tenant_id,request_id)`，并显式 `NOT VALID` 后立即 `VALIDATE CONSTRAINT`。应用 `BatchDayGateService.waitLaunch` 用 `LaunchRequestIdentityGuard` 对照同一 tenant/request 及 job、Workflow、bizDate、dryRun 和原请求可接受状态；FK 只保证父请求同租户存在并限制删除/改键，这些启动业务字段仍由应用负责。请求保留清理先删到期终态等待子行，再删请求；活跃、未知或近期等待保留，wipe/seed/SDK清理均先删子行。真实 PG 应用与 scheduler 定向回归37/37通过。该条只形成局部应用/数据库契约，不关闭 REF-04/DBSAFE-3；全量 Squawk 对71个迁移报告15条告警，SIM、部署与剩余引用仍开放。

V311 将 `batch_day_catchup_control(tenant_id,calendar_code)` 以复合 `NO ACTION` FK 绑定到 `business_calendar` 同租户自然键，`NOT VALID` 后立即验证；应用按相同租户和日历编码预检 enabled 日历。真实数据库父侧删除/改键由 FK 拒绝；新增的真实双事务交错用例证明父删锁等待、删除提交后应用返回409且无控制行/审计副作用，应用单测也覆盖指定约束 `23503` 的稳定映射。软停用保留控制状态；租户 wipe 和克隆按审计、控制、日历的子先父顺序清理。真实 PostgreSQL 首红及 189 项受影响回归结果、后续真实竞态1/1与日历类/服务单测28/28复跑见[验证矩阵 V311](workflow-daily-integration-execution-log-2026-10-14.md)。该局部证据不关闭 REF-05/DBSAFE-3，也不代表全量 SIM、容量或目标部署已验收。

#### 逐关系对照

复用逐表引用清单，为每条关系记录以下内容；同一关系的应用校验与数据库约束必须使用同一业务身份，不能分别按裸 ID、同名 code 或不同业务日查找：

| 对照项 | 应用层责任 | 数据库责任及边界 |
|---|---|---|
| 引用身份 | 按 tenant、父对象 ID/自然键及关系要求的 Workflow/JobInstance/Pipeline、bizDate、版本或类型解析目标；区分全局与租户配置。逐列对照 FK 子键顺序与父候选键，不能只验证“父对象存在” | 在可表达的强关系上以 FK/UNIQUE/CHECK/NOT NULL 保护相同身份；分区键按真实唯一键处理，RLS 不能替代父子归属约束 |
| 空值与草稿 | 对齐缺省、NULL、空串、可选引用和草稿规则；启用/发布/执行入口执行对应的完整校验；复核应用是否允许部分 NULL 组合绕开必填身份 | 明确组合 FK 的 `MATCH SIMPLE/FULL`、逐列 NULL 行为及所需 NOT NULL/CHECK；草稿合法不等于缺失引用可进入执行 |
| 业务状态 | 校验 enabled、软删除、可用版本、节点/资源类型、依赖环及同业务对象归属；父配置变化时按既定策略阻断或重新校验 | FK 只保证所声明的引用完整性，不自动保证启用状态、JSON 语义或无环；需要持续保持的业务不变量另有事务/状态协议 |
| 父键变更、删除与归档 | 对齐父键更新、停用、软删、物理删除、归档和恢复入口；按已裁定策略阻断或执行子行处理，保留等待/重试/运行快照及取证引用 | 逐条记录并核对 FK 的 `ON UPDATE`、`ON DELETE`、可延迟属性及约束验证状态；RESTRICT/NO ACTION/CASCADE/SET NULL 的实际效果不得与应用行为冲突，历史快照不得因热父对象归档消失而被误判失效或连带删除 |
| 弱引用与例外 | 记录历史快照、多态/JSON、跨库、外部身份及 system/global 例外的所有者、读写/清理入口、巡检与恢复策略 | 有意不加 FK 的关系必须说明原因及替代保护；不伪造跨库 FK，不把仅有子侧 EXISTS 的检查称为等效外键 |

对照清单还须列出应用 Service/Guard/Mapper、DDL 约束名或触发器、父侧变更路径、事务边界、错误码、关联测试及当前状态。优先核对 Workflow JOB、等待请求与原请求/业务日、运行子树归属、Job 依赖、日历/队列/模板等活跃配置关系；沿用已有 REF 编号承接，不新增一套重复验收计数。**没有应用写入口也是一种有效状态，必须明确记录；不能把DB约束写成已经由应用层重复守护。任何后续新增写入口须在相同租户/父键和事务竞争协议上先行校验，并将数据库兜底冲突转换为与应用预检一致的领域错误。** `calendar_dependency` 的实际例子和后续写入口验收见[逐表方案 §2.17](database-reference-integrity-remediation-2026-10-18.md)。

#### 逐关系交付记录

每条引用沿用已有 DBSAFE/REF/RT 编号，在对应专题中维护一条可复核的记录，至少包括：`子表/字段及列顺序 → 父表/候选键及列顺序；tenant/聚合/业务日身份；MATCH 与 NULL/草稿规则；ON UPDATE/ON DELETE/可延迟语义；应用 Guard/Mapper 及全部写入口；约束名、验证状态和删除动作；父侧变更/归档/清理入口；事务与锁顺序或 CAS 协议；应用错误码 ↔ 数据库 SQLSTATE/约束身份映射；正反例/双事务证据；剩余缺口`。逐关系核对应用守护和实际 catalog 中的结构语义；如果业务规则有意比 FK 更严格，单独列出规则及适用入口，若较宽则视为缺口，不能用概括性的“已有校验”掩盖差异。标明各项属于原生数据库保证、应用业务规则或有意保留的弱引用；未具备的保护写为待实现。

**应用/数据库配对状态必须逐关系登记，不能留空或从一层推断另一层**：

1. **应用写入口存在且关系是强引用**：列出每个 Service、Mapper、导入/复制/初始化及运维写入口；守护按数据库 FK 的同一候选键、租户/聚合身份和可空规则解析父对象。数据库拒绝应用预检已接受的并发写入时，应用须回滚整个事务并映射为稳定领域冲突；应用专有的 enabled、软删除、状态、业务日或类型规则单独列出，不能伪装成 FK 语义。
2. **当前没有应用写入口**：明确记录“DB-only”，列出可写的直接 SQL、迁移、种子或运维路径；不能声称已有应用守护。将来增加应用入口时，须在同一变更中补齐身份一致的 Guard、竞态错误处理和应用/真实 PostgreSQL 正反例。
3. **有意不建立 FK 的弱引用或例外**：记录不加 FK 的原因、可接受的失配状态、责任写入者、读取/清理/巡检/恢复方式及告警；若应用仍校验目标，说明该检查保护什么、并发下不保证什么，不能称其等价于数据库约束。

验收时应以“数据库关系清单 × 应用入口清单”逐项交叉核对，确保没有未分类关系、遗漏写入口或只在单侧存在的强引用声明。除应用 Guard 与持久化值身份相同外，还要将 Guard 的父键读取条件、NULL 处理、父侧更新/删除策略及数据库拒绝映射，与迁移后实际 catalog 的 FK 定义逐项对照。应用预检测试应断言最终持久化的租户及父键与所验证的身份相同；另用数据库直写负例证明 FK/触发器仍能独立拒绝违规记录，并用并发父删/改键场景证明事务边界及错误契约。合法正例、重试、恢复和清理顺序也必须通过，避免守护过严导致新回归。该矩阵是 DBSAFE-3 的验收产物，不新增 REF/R 项或完成计数。

- 应用校验或数据库约束任一侧调整时，同步复核另一侧和父侧生命周期。应用提前拒绝与数据库兜底应对齐引用身份及错误契约；enabled、软删除、依赖环等应用专有规则另列验收，不要求 FK 承担其无法表达的语义。
- 原生 FK 尚未落地的强关系不得标为数据库已保护；应用锁/CAS 方案必须列明覆盖入口与仍可绕过的 SQL/维护路径。保留期删除、归档或分区淘汰协议未闭环时，该关系继续开放，不能仅因子侧写入校验通过而关闭。
- 每条记录分别标记设计、实现、定向测试、真实 PostgreSQL 并发及适用目标环境的状态与证据。正例必须证明合法写入、重试和恢复仍可成功；只有负例被拒绝，不能排除守护过严造成的回归。联合验收沿用既有编号，不新增完成项。

#### 全入口与并发规则

- 追踪创建、更新、UPSERT、批量导入/复制/初始化、启用/发布/启用日程、Trigger/Orchestrator 启动、补跑/重试/恢复及归档清理。复用现有领域校验与持久化入口；跨模块按既有所有权调用，不为“统一守护”引入通用动态 FK 框架或让 Worker 直接修改编排状态。
- 活跃引用校验必须在正确的写库、租户及事务上下文中执行；不能用只读副本或缓存的存在性结果作为提交依据。应用 `SELECT EXISTS` 后再 INSERT 即使在同一事务也不能单独消除父删除/更新的竞态。
- 能用原生约束表达的引用交由数据库约束兜底。对软删除/停用、图约束和合法弱引用，明确父子写入、父更新/删除、归档及分区淘汰共享的锁/版本 CAS/状态封口协议；统一锁顺序，并用双事务交错证明。不要求所有关系一律加锁，也不把单边触发器当完整协议。
- 同一事务中的校验失败必须回滚关联记录、状态与 Outbox，状态更新影响 0 行按约定识别冲突或幂等结果，不能默认成功。跨数据库/服务的动作单列补偿、恢复和可观测状态，不假设本地回滚能撤销已发生的业务副作用；PROCESS staging 仍按 §3.3 治理。
- 运维 SQL、迁移、批量 Mapper 及特权路径单独核查：受数据库约束表达的强不变量不得被旁路破坏；应用专有业务规则若允许维护入口绕过，必须有明确前置校验及停流/恢复边界，不能静默豁免。
- 数据库兜底拒绝与应用提前拒绝应映射到同一对外业务契约：沿用既有 `ResultCode`/HTTP 约定，FK 冲突对齐现有 409 处理；优先根据 SQLSTATE/约束身份分类，未知完整性错误不得吞掉、记成功或无限重试。跨租户不可见与不存在的反馈遵循既有权限规则，不向调用方泄露原始 SQL、父行数据或其他租户身份。

#### 定向验收与防漂移

1. 为同一关系准备独立预期：同租户合法、缺失父对象、异租户、错聚合/业务日、NULL/草稿、停用/软删、父键更新/删除、历史快照及多态/跨库例外；逐项对照应用查父键条件与 FK 子键/父候选键、MATCH/NULL、ON UPDATE/ON DELETE 语义。应用与数据库只在各自声明的保证范围对照，不能要求 FK 替代业务状态校验。
2. 分别通过应用 API/导入入口和真实 PostgreSQL 直接 INSERT/UPDATE/DELETE 验证；SQL 旁路必须拒绝违反已声明数据库不变量的记录。使用普通应用等价角色和显式事务租户绑定，不用 superuser 或 Mock 作为隔离证明。
3. 双事务测试覆盖子写与父删/停用/改键、父归档与新增子记录、两个依赖更新合成环；断言无非法提交、无部分写入、无错误 Outbox/任务派发，并验证合法重试、归档及恢复仍可完成。
4. 对照迁移后的实际 catalog、Mapper 条件及应用入口，补能发现“漏守护/漏约束/键或删除语义不一致”的回归；预期值不能全部从同一份被测实现自动派生。约束或 Guard 改动时同步更新对照、失败用例和领域文档。
5. 按关系记录实现、单测、真实 PG、应用链路及目标环境证据；现有局部通过不自动关闭 DBSAFE-3、REF 或 R20/R33/R36。尚未实施或未运行的场景保持开放。

### 3.3 PROCESS staging 与分区清理安全

- staging `batch_key` 默认与 `process-<taskId>` 相关，但执行入口支持显式 payload batchKey，不能只解析字符串推断所有者；staging 在业务库、任务状态在平台库，仅按 `staged_at` 年龄删除行或整日分区，不能证明任务已终态或恢复窗口已结束。
- 主线须沿 PREPARE/COMPUTE/VALIDATE/COMMIT/FEEDBACK、checkpoint 跳过、重试、Worker 崩溃、任务超时、跨日恢复及手工补数路径确认 key 与状态的真实关系，并明确可恢复保留期。
- 在生命周期事实可查询、可原子判定且覆盖跨库故障边界前，不得把固定年龄当作唯一删除授权；DROP 整分区前还须证明其中无在途、等待恢复或审计保留数据。若暂时做不到安全门控，明确收紧或暂停自动删除，并评估存储增长、容量告警和运维处置影响。
- 真实 PostgreSQL 验收覆盖长于默认保留期的在途任务、失败重试、等待恢复、终态清理、跨日、分区边界与并发写入；证明被保留数据可以继续 COMMIT/恢复，终态数据按策略回收。
- **当前保护**：`batch.worker.process.staging-cleanup.deletion-enabled=false` 为默认值；未建立跨库批次生命周期证明前，行 TTL 与整分区 DROP 均不执行。调度和分区预建可继续，启动审计暴露是否启用删除及超期行数。该失败关闭不等于 PART-02 完成，且须单独评估保留导致的磁盘增长与运维处置。

### 3.4 其他分区与跨日引用

- 逐项核对 `job_instance`、workflow/outbox 等分区的分区键、DEFAULT、预建窗口、迟到写入、时区/DST、跨日查询/重放、归档与删除行为。
- 核实父级主键/唯一键是否包含分区键，以及 FK、ON CONFLICT、冷热回读是否依赖其语义；不为增加 FK 改变幂等或分区身份。
- 验证新分区继承必要索引/约束/RLS，创建幂等，DEFAULT 积压可发现与迁移，分区维护不会和运行事务/归档争锁。

## 4. P2/P3：索引审查与优化

- 以 Mapper SQL 和真实调用负载为单位记录谓词、排序、LIMIT、锁语义、租户前缀和状态分布；热点查询采集代表性参数下的 `EXPLAIN (ANALYZE, BUFFERS)`，覆盖 prepared/generic plan、积压峰值及大小租户差异。
- 优先复核 JobInstance 日期列转换、Webhook 重试状态谓词与 partial index 不一致，以及调度/归档/lease/告警/补偿扫描。先保证查询语义，再决定是否新增或调整索引。
- 评估在线构建、锁、WAL、空间、写入放大、分区索引有效性和失败残留。候选索引必须证明不承担唯一性、FK 目标、ON CONFLICT、稳定排序或关键恢复查询后才能删除。
- 区分约束索引和查询索引；分区父索引扩展数不能简单视为重复索引。DROP 必须单独迁移、回退/恢复说明及目标环境统计证据。

## 5. 联合验收矩阵

| 验收组 | 必备证据 | 不足以关闭的证据 |
|---|---|---|
| DB 基线 | 实际 catalog：表/列、FK、唯一/检查约束、索引定义与有效性、分区树/bounds、RLS/policy、角色属性、Flyway 版本 | 仅从迁移源码推断实际结构 |
| 租户隔离 | 普通应用角色对父表及每个叶子直接读写跨租户正反例；strict/rollback/新叶子守卫测试 | superuser 测试、只测父表、ThreadLocal/Mock |
| 引用完整性 | 实际约束与逐关系对照、租户/聚合键、空值及删除动作、新库初始化验证；适用的正常升级预检与 VALIDATE | 只有 Service 校验或单测，按字段后缀机械补 FK |
| 应用守护一致性 | §3.2 全入口覆盖；应用与 SQL 对同一身份的正反例；业务状态及弱引用例外；双事务父子写/删/归档；错误契约与无部分副作用 | 只在 Console 单条入口校验、子侧 EXISTS、两层都读同一常量的同源断言 |
| 归档恢复 | 行数和字段快照对照；独立 Workflow 与 Job 归档；故障时热数据保留；冷回读关联验证 | 只检查 archive 表存在或 XML 可解析 |
| 清理跨日 | 在途/重试/等待恢复/跨日任务保留；终态清理；午夜/DST/迟到/重放；并发分区维护 | 仅测默认 retention 内小样本 |
| 索引容量 | 代表性负载、真实查询计划、延迟/锁/WAL/空间/写开销和分区扩展证据 | 空库 `idx_scan=0` 或单一 EXPLAIN |
| 发布恢复 | 全新数据库初始化与接流量顺序、失败续跑、备份恢复与回切边界，需 DBA/目标环境操作项；上线后新模型升级另行验收 | 仅 Testcontainers 即宣称生产迁移通过，重新引入旧系统兼容 |

分别记录静态检查、单元测试、真实 PostgreSQL 集成、SIM/E2E、staging/生产证据；未运行、环境阻塞和需 DBA 批准的 DDL 单独列出。

## 6. 主线推进清单

1. 合并 feature 分支已有逐表外键、索引、分区证据并核对当前实际 schema；统一编号和事实来源，避免多个报告重复计数或相互冲突。
2. 复核主线当前归档改动，完成 `workflow_node_run.job_instance_id` 字段保全和真实 PG 回归；同步落实分区叶子 RLS 与普通角色负例。
3. 完成 PROCESS 生命周期调查，再裁定安全清理门控；明确平台库/业务库边界、重试、checkpoint 和跨日恢复，不以年龄阈值替代终态证据。
4. 按逐表裁定完成 FK 与应用守护对照、全入口和双事务验收，约束按新库初始化顺序落地；正常升级另做适用的预检/验证。按真实计划逐项处理 P2 索引，不机械全量加/删索引。
5. 同步总待办、数据库治理文档、RLS/分区 runbook 和验收报告；只有实现和对应证据完成后才能关闭条目。
