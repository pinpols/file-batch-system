# 平台库 Flyway 重编号方案

用户确认新系统允许从空库重建。以 `0da30d0f2` 的原迁移链 V389 为结构对照。重编号只影响平台库的部署迁移，业务库继续使用独立初始化入口。运行数据库的重建由部署流程另行授权。

## 目标

- 平台库从 V1 开始初始化。V1 建模式边界，V2 创建完整平台结构和种子数据。后续变更从 V3 开始。
- 新链集中定义当前表结构，包括冷热表、Quartz、RLS、函数 ACL、触发器和按安装月份创建的分区。新库初始化过程中无退役表。
- 原链保存原校验和且退出运行包，用于只读审计和按历史版本验证。任何具备旧迁移历史的数据库需要先走明确的备份与重建流程。
- 让启动校验、打包和 CI 明确读取新链，保留历史迁移专项测试的覆盖。切换后继续禁止改写已发布迁移。

## 验收

1. 用真实 PostgreSQL 对照原链 V389 与新链空库的全量结构清单、种子、对象权限及动态分区。核对保留对象的定义及生命周期。
2. 验证 Flyway 空库初始化、重跑零变更、校验及旧历史拒绝。覆盖 Docker 预创建模式和非超级用户迁移身份。
3. 验证迁移资源只打包新链，Orchestrator 和 Trigger 从新库通过启动校验，并复跑保留的迁移用例。

## 部署与恢复边界

使用干净构建生成各服务的运行包，核对平台迁移资源只包含 V1、V2。已有部署若需要保留数据，先停写并备份旧库，保留对应版本的运行包和配置。部署新平台库并完成权限、调度和业务验收后再切换连接。切换后已有新写入时，恢复前先处理数据对账。旧链用于恢复旧版本和核验新结构，禁止把旧 history 当成 V2 已应用的证明。
