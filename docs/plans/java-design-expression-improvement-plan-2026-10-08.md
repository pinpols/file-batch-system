## 2. 设计原则与不变边界

学习成熟 Java 项目的重点是清楚的契约、生命周期和责任归属，不是把所有类都改成相同形状。

### 2.1 四项核心思想与评审标准

| 思想 | 本工程的落地判断 | 反例 | 验证依据 |
|---|---|---|---|
| 高内聚 | 同一组件围绕一个业务责任和变化原因；调用方不必了解无关职责 | 十四个依赖换成多个 record，但主服务仍操作全部依赖；按文件长度任意切分 | 职责/依赖使用图、受影响规则的修改范围、窄单测是否需要无关 fixture |
| 信息隐藏 | 隐藏会变化的实现选择，暴露稳定的业务操作；关键顺序仍在用例入口可见 | 调用方依赖协作者内部 Map key、存储实现或跨多层转发才能找到事务边界 | 消费点核对、固定契约测试、实现调整是否迫使无关调用方同步修改 |
| 资源所有权明确 | 每项线程、流、文件、连接有明确创建者和关闭责任；借用资源不越权关闭 | 方法接收外部流却自行关闭；启动部分失败无人回收；把共享容器资源重复关闭 | 所有权表、部分启动失败/关闭异常/超时取消测试、线程与临时文件回收证据 |
| 依赖方向稳定 | 沿用现有领域/应用/端口/适配器边界；技术实现依赖稳定契约，不反向污染核心 | 领域层直依赖 JDBC/HTTP 实现；SDK 为复用 DTO 依赖平台应用；循环注入靠 Lazy 掩盖 | 模块依赖与架构测试、公开签名检查、Spring context 无循环装配 |

信息隐藏不是隐藏异常、锁或副作用；依赖方向稳定也不是“每个类必须有接口”。只有真实替换、边界隔离或测试价值才增加接口。依赖数量、代码行数和模式数量都不能单独证明这四条已经做到。

### 2.2 实施约束

1. 先证明问题，再选择抽象。新增类型或协作者必须减少实际理解成本、隔离独立变化原因或保护不变量。
2. `record` 适合数据载体，但把十四个依赖装进一个 record 不等于降低耦合；不得用参数数量变化代替职责改进。
3. 保留能清楚表达业务顺序的长方法和声明式规格。只有阶段边界清楚或嵌套妨碍理解时才提取。
4. 条件提取使用业务名称，例如 `hasHardCap`；不用 `isOk`、`flag` 掩盖条件，也不为一次简单判断制造间接调用。
5. 中文注释说明为什么、哪些顺序不可变、失败后谁负责恢复；移走代码后同步移走注释，删除失去上下文的阶段编号。
6. Spring 管理生产协作者与资源生命周期；测试 fixture 负责测试组装，不在生产类中累积仅供测试的装配分支。

所有实施批次均不得顺手改变：

- 租户校验、RLS、鉴权、幂等键、CAS、advisory lock 和终态语义。
- `@Transactional` 入口、传播级别、回滚规则、Outbox 顺序和 after-commit 行为。
- Worker claim/report、Kafka offset、lease、取消、checkpoint 和资源关闭顺序。
- 公开 Java 签名、HTTP JSON 字段、缺省/空值行为、错误码和动态 workflow 输出。
- 默认配置、数据库结构、依赖版本、格式化风格和模块依赖方向。

若其中任何一项确实需要变化，停止按纯重构推进，拆成独立行为或兼容性变更并补充设计及测试。

## 3. 首批核查清单

以下是当前工作区源码抽样事实，不是已发现的运行故障。代码可能被并行任务修改，实施前须重新确认。

| 编号 | 位置 | 核查事实 | 裁定 |
|---|---|---|---|
| JD-1 | `batch-worker/import/.../stage/PreprocessStep.java` | spool 阈值注释落在 `ERROR_OBJECT_MAPPER` 上，单文件限额注释落在 `fileRecords` 上 | 修正注释归属；数值与来源须以当前属性类为准 |
| JD-2 | `PreprocessStep`、`DefaultTaskOutcomeService` | 便利构造器会手工组装协作者；Task Outcome 已注明用于纯单测 | 调查所有调用方，再将纯测试装配迁入 test fixture；不是直接删除所有重载 |
| JD-3 | `sdk/java/core/.../client/BatchPlatformClient.java` 的注册载荷 | 固定字段使用 `HashMap.put`，部分指纹字段按存在性加入，空描述列表被省略 | 优先核对已有 `RegisterRequest` 是否可复用，保持实际 JSON 形态与 SDK 边界 |
| JD-4 | `TaskOutcomeCommand.verifierFailures` | 固定 `{code, message, evidence}` 元素使用 `List<Map<String, Object>>` | 调查 Worker、内部接口、Outbox 的完整传播路径；固定元素类型化，开放 evidence 不强行封闭 |
| JD-5 | `TaskOutcomeCommand` | `success` 与成功/失败字段共存，允许构造语义不一致的组合 | 先建立兼容行为测试，再评估内部成功/失败结果类型；不能直接收紧旧请求校验 |
| JD-6 | `DefaultTaskOutcomeCollaborators` | 聚合十四个依赖，服务及进度协作者共同消费 | 先画真实使用关系，只提取有独立责任的协作者；不增加多个纯依赖容器 |
| JD-7 | `FairShareGroupAdmissionGuard` | 已用业务谓词及中文原因注释区分观察容量与锁内准入 | 作为正向样例保留，不为统一形状继续拆分 |

固定载荷的类型所有者必须由消费路径决定。SDK core 保持 Spring-free，不因 DTO 复用依赖平台应用模块；平台领域类型不反向依赖 SDK。

## 4. 分阶段实施

### 阶段 0：确认调用图与行为基线

**交付**：每个候选记录生产/测试调用方、类型所有者、现有测试、兼容范围及不变语义。特别核对 Java SDK 的公开签名与平台协议、Task Outcome 的重复/乱序报告和事务入口。

按 §2.1 同时记录：组件业务责任、隐藏的实现选择、资源创建/借用/关闭责任以及允许的依赖方向。资源表至少包含“资源 / 创建者 / 使用者 / 关闭者 / 部分启动失败处理 / 清理失败处理”；没有涉及资源的候选标为不适用，不为表格完整虚构所有权。

**完成条件**：候选被分类为“实施 / 合理保留 / 需行为设计”；固定载荷有当前序列化基线。被其他任务做掉的候选登记证据后退出，不重复实现。

### 阶段 1：注释与业务表达（JD-1）

**交付**：修正 `PreprocessStep` 两处错位注释，核对相关属性类、对象读取协作者的注释是否准确；只清理当前改动范围内失去意义的历史编号，保留必要 ADR 引用。

**完成条件**：注释的字段归属、配置名称、单位和禁用语义与实现一致；diff 不含行为或无关格式调整。

### 阶段 2：生产装配与测试装配分离（JD-2）

**交付**：为两类复杂对象建立所属模块的 test fixture，迁移纯测试便利构造器的调用方；生产入口只使用受容器管理的协作者。优先显式构造依赖，不引入万能 factory 或运行时 locator。

**兼容约束**：确认重载不是 SPI、插件或外部消费者入口后才能删除。无法证明时先保留、登记消费者，不以“没有仓库内调用”证明外部兼容。

**完成条件**：受影响测试不依赖生产兼容装配，真实 Spring context 验证唯一注入入口及关键 Bean 的生命周期；不得以全 mock fixture 代替容器装配验证。

### 阶段 3：固定载荷类型化（JD-3、JD-4）

拆成两个独立批次：

1. Java SDK 注册载荷：优先复用现有请求类型；若字段不匹配，在 SDK 所属传输边界定义类型。保留指纹字段缺失、`taskTypes` 空列表省略、时间字符串、能力标签和协议版本语义。
2. verifier failure 元素：固定 code/message/evidence 结构，明确 evidence 中仍允许动态数据；保留原列表顺序、null/empty 和每项 Outbox 事件语义。

**完成条件**：使用实际 HTTP 客户端的序列化配置比较前后 JSON，而不是仅比较 `new ObjectMapper()`；核对请求/响应两端和持久化事件。若涉及 OpenAPI 或共享 wire，同步契约与所有受影响语言消费者，不能只完成 Java 编译。

### 阶段 4：任务结果不变量建模（JD-5）

**交付**：在现有传输 DTO 后建立窄内部结果模型，区分成功与失败载荷；可选 sealed 类型，但不得仅为使用语言特性引入抽象。旧 DTO、Builder 和公共协议先保留，在边界转换后使用内部类型。

**重点**：成功路径仍允许 verifier failure 证据，不把它误建模为任务执行失败；失败分类缺失仍按原规则推断；历史输入中被忽略的字段继续按原语义处理。

**完成条件**：内部代码无法无意混用两类专属字段；重复报告、CAS miss、租户不符、invocation 不符、成功/失败和补偿路径与旧行为一致。不改变旧输入接受范围。

### 阶段 5：协作者内聚与整体验收（JD-6）

**交付**：根据阶段 0 调用图，确认哪些职责已经由 terminal finalizer、DAG progressor、instance progressor 等现有协作者承担。仅当主服务仍穿透这些职责或测试必须装配无关依赖时继续下沉；没有收益则保留并记理由。

**禁止**：把十四个依赖机械分成多个 record；为缩短构造器新建单方法转发壳；改变事务或消息顺序；形成协作者循环或把组装职责下沉到领域层。

**完成条件**：每个抽取有独立变化原因与窄测试，主入口仍能直接读出状态推进顺序；所有清单项完成或有保留裁定，完成下述验收后才能标记 Implemented。

## 6. 不做与暂缓

| 项 | 裁定 | 原因 / 重新评估条件 |
|---|---|---|
| 全工程改 sealed / record / Optional | 不做 | 语言特性不能替代语义设计；只在明确载荷或封闭分支使用 |
| 全部 Map 改 DTO | 不做 | 动态 metadata、JSONB、插件参数、workflow outputs 和测试 fixture 保留 |
| 以行数、构造参数数量、方法长度作为硬 KPI | 不做 | 会诱发依赖容器、空接口与方法壳；以实际理解和测试成本评估 |
| 全局条件和 inline 对象机械提取 | 不做 | 只提取多层嵌套或有业务名称的判断/载荷，不破坏表达局部性 |
| 重换格式化工具或模仿 Spring/Apache 排版 | 不做 | 保持既有 Spotless 风格，避免无关 diff |
| 新增全仓强制风格门禁 | 暂缓 | 先人工清单与报告；确有新增漂移且误报可控才扩展现有守卫 |
| 服务物理拆分、公共万能 DTO/Constants、额外配置中心 | 不做 | 与本轮代码表达目标无关，会扩展运行和依赖复杂度 |

## 7. 交付、风险与回退

- 实施顺序：0 → 1 → 2 → 3 → 4 → 5；SDK 注册与 verifier 元素分别交付，不混成一张大 PR。
- 每批在实施前重新检查工作区、消费者和已有 PR，保留并行改动。本方案不授权自动提交、推送、合并或清理分支。
- 每批只含一个职责或契约簇；注释、测试装配、载荷类型和状态模型分别提交。结构调整不夹带算法与默认值变化。
- JSON 漂移通过实际序列化快照防护；公开构造器删除先核对兼容；事务、锁与 after-commit 由真实 PG 测试验证，不凭代码形状判断。
- 纯内部变更不迁移数据库，回退按独立批次提交进行；已发布 SDK 的公开签名变化不得当成内部重构回退处理。
- 每阶段记录 SHA、验证命令、结果与未运行项；本地通过、PR checks、main Full Gate、sim 和生产验收分别记录。

### 9.2 流程方法保留判据

较长的流程方法可以保留，但应同时满足：

1. 单一用例，执行顺序本身具有业务意义，读者能从主入口看到关键阶段。
2. 技术细节由具名协作者承担；主入口不重复展开序列化、存储或重试实现。
3. 异常处理和清理与资源所有者相邻，不通过多层转发隐藏提交、回滚或关闭边界。
4. 扩展点明确，不允许子类绕过必要的安全检查和持久化顺序。
5. 有行为测试证明顺序、失败和清理语义，不用“模板方法模式”替代验证。

对 `runStageLoop` 的初次评审应先画出“加载定义 → 续跑判断 → 记录开始 → 执行 → 记录结果 → 选择下一步”的现行顺序，再核对 cycle guard、多分区降级与产出回灌。只有细节妨碍主流程阅读时才提取，不能把每一步包成一个无独立职责的方法。
