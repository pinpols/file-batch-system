# 系统设计核查与容量验证计划

日期：2026-11-09

状态：按用户选择以现有本地结果收口；六个工作包均有局部证据，原 G1–G4 的完整验收未完成。容量、故障恢复和目标环境的缺项另行验收；本记录不代表生产性能或发布验收通过。

## 目标和原则

围绕实际业务链核查设计和实现，先排除会使压测结果失真的关键正确性问题，再以小负载验证完整闭环，随后分层测容量和恢复。系统设计细节多，按有限工作包分批推进，核查与压测可交错，不以全工程逐文件审查作为开始压测的前提。

本计划覆盖后端、Console、相关 SDK 及其依赖和部署边界。工程规约、纯外观优化和没有实际场景支撑的防御性改造不作为本轮主要目标；发现问题时记录具体触发条件和业务影响，评审不自动授权实施。真实环境部署、负载、故障注入、数据清理及代码修改另按具体任务和环境授权执行。

## 范围：六个工作包

每包按“业务入口 → 状态及持久化 → 跨组件传递 → 实际副作用 → 失败、重试和恢复 → 用户可见结果”核查，记录适用场景、证据及结论。状态统一使用：已证实、已排除、待验证、已接受的取舍；无法适用的场景说明原因。发现的问题按影响和证据排序，规约候选单独登记，不把搜索命中数当缺陷数。

| 编号 | 工作包 | 核查重点 | 最小证据 |
|---|---|---|---|
| S1 | 触发、业务日与预期 | 手动、定时、事件和文件触发；业务日、幂等身份、迟到、预期履行与日结语义 | 相同及不同业务身份的触发到持久化结果；预期与实际运行关系 |
| S2 | Workflow 与依赖 | 运行快照、节点状态、依赖与分支汇合、WAIT、超时及文件/事件等待 | 代表性正常、等待、失败和恢复路径的状态及可见结果 |
| S3 | 调度与控制面 | 租户隔离与容量、排队、事务和 Outbox、消息、认领、续租、回报、批量逐项语义 | 请求到运行、任务及结果的身份对账；失败隔离与重试证据 |

## 阶段与门槛

### 0. 锁定场景与环境

1. 记录前后端及关联 SDK 构建版本、部署拓扑、依赖版本、资源规格、关键配置、业务日与时区；标记现有改动和数据来源。
2. 确定本批租户、作业和 Workflow、Worker 类型、数据量、到达模型、并发或到达速率、持续时间、业务成功条件和性能目标。未确认的业务规模、SLO 和阈值保持待定，不沿用工具默认值冒充目标。
3. 确认环境隔离、资源预算、观测方式、停止条件和数据归属。执行前审查现有造数、配置变更和清理动作；只允许明确范围的测试数据与资源，清理需先预览并获得相应授权。共享环境中的画像串行执行。

**G0：** 场景、身份口径、版本和环境可追溯，执行与清理边界明确。目标环境或相关操作未授权时只完成准备，不启动负载或故障注入。

### 1. 关键正确性核查与定向验证

按 S1–S6 建立链路证据和问题清单，优先处理可能产生错数据、跨租户影响、重复/丢失副作用，或使容量结果失真的问题。文件等待先核对：

- 渠道配置应表达具体渠道还是来源类型，以及现有数据和 scanner 登记身份是否匹配；用适用样本验证错匹配和漏匹配，不预设改造方案。
- 隔离数据中验证前 200 个对象持续保留时，新对象能否被后续扫描处理，同时覆盖适用的轮询、事件、完成标记、稳定窗口与重启路径。

其他工作包按实际业务风险选择最小验证层级：纯逻辑用单测，事务、SQL 和并发用真实数据库集成验证，跨组件传输或真实副作用按场景选择集成/端到端验证。仅对发现或修改的问题运行相关测试；历史证据须标明版本、环境和局限。

**G1：** 本批关键链路的业务语义和成功口径明确；会导致结果错误或无法对账的阻断问题已验证处理，或将对应场景明确排除并记录影响。其他非阻断问题进入清单，不等待所有低风险细节完成。

### 2. 小负载完整闭环

先验证测试工具、数据和观测是否有效，再用受控小负载贯通触发、调度、Worker、真实业务副作用和前端查询；分别覆盖同一业务身份的幂等重试和合法的不同业务身份。按所选场景检查租户边界和 Worker 路由，不用更改业务日或身份绕过去重。

逐项对账总请求、准入、拒绝（含限流）、去重、失败、超时和结果未知；对已接受的请求追踪运行、任务、终态及应有的数据或文件副作用。成功、失败和未完成分别计数，超时不能从总结果消失；故障场景中的预期失败也必须与副作用一致。复用已有控制面画像的身份对账能力，补足所选场景所需的 Worker 和业务结果证据。

**G2：** 已接受请求全部可分类并完成身份及业务结果对账，稳定场景没有未解释的丢失、重复副作用或未知结果；拒绝率和失败率按约定目标判定。若无法完成对账，先定位原因，不将 HTTP 成功或部分终态比例作为闭环通过。

### 3. 分层容量与稳定性

在 G2 通过的场景上逐级施加约定负载，并保留相同环境、数据规模和配置下的可重复基线：

1. 控制面：触发受理、独立运行创建、调度队列和回报；同时区分重复业务请求与新增业务工作量。
2. Worker：按适用类型分别测试真实执行、续租、结果回报、文件大小/数量和业务副作用。
3. 混合负载：多租户、触发与执行并行，并观察查询和关键用户操作；记录队列积压与最早等待时长，评估公平性。
4. 稳态与恢复：在约定时长内观察资源、积压和业务完成情况；负载回落后核对排空及结果。真实故障注入和部署切换仅在边界确认后单独安排。

每次记录总请求及各分类、准入和完成吞吐、端到端及接口 p50/p95/p99、失败/超时/拒绝、积压及其趋势、Outbox 与消息滞后、数据库连接/锁、Worker 和基础设施资源，并保留业务对账结果。记录造数规模、压测机资源和采样时间；避免压测机自身成为未知瓶颈。相同条件下重复测量，说明波动、异常及环境限制。

**G3：** 按事先约定的业务成功条件和性能目标判定；未约定指标目标时只产出容量基线，不声称通过生产容量验收。本地、预发布和生产证据分别报告，不能互相替代。

### 4. 故障与运行边界

依据前述实测瓶颈和真实运维场景，选择进程退出、依赖不可用、消息或回报延迟、维护停机与恢复等有业务意义的场景，核对状态收敛、业务副作用、积压恢复及告警触发/解除。维护期是否抑制告警按现有维护语义和约定场景验证，不能一概关闭。

**G4：** 所选场景有明确预期、过程与恢复证据，遗留风险和目标环境差异均已记录；未执行的场景保持待验证。
