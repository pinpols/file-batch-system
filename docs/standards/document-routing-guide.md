# 文档查找与变更路由

> 类型：长期文档资产；直接维护原文。本文回答“去哪里找、系统改动后更新哪里”。日期、归档和证据规则以 [文档治理规范](document-governance.md) 为唯一规范。

## 1. 先确定更新方式与生命周期

| 生命周期 / 产物 | 去哪里 | 如何更新 | 文件名日期 |
|---|---|---|---|
| 长期系统资产：架构、模型、原语、契约、设计、手册 | 该领域的 architecture / design / api / sdk / runbook | 修改原文，反映当前事实；决定和版本变化按 ADR / Changelog 追溯 | 不带日期 |
| 长期工作台账：当前待办、持续硬化 | plans/todo-master.md、plans/hardening-backlog.md | 原文件更新状态、优先级、来源、证据和下一步 | 不带日期 |
| 阶段性改造方案、验收矩阵 | plans/ | 同一阶段维护原方案和矩阵；调整范围或状态写明时间与依据 | 保留原始完整基线日期 |
| 阶段性执行日志 | 与所属方案同置的 plans/ 日志 | 追加批次、命令、结果和边界；不覆盖此前证据 | 保留阶段基线日期，批次时间写正文 |
| 每轮代码审查 / 专题审计 / 验证结果 | review/ / audit/ / verifications/ | 每一轮新建日期记录，反链对应系统资产或方案 | 带本轮日期 |
| 被替代的方案、已结束探索和旧结果 | archive/ | 保留当时结论与日期；当前剩余事项回到台账，历史材料不继续充当当前状态表 | 带原日期，不改为归档日期 |

长期/阶段性表示保留和维护周期；原文更新/增量记录表示更新方式。阶段方案也会维护原文，执行日志则按批次追加，不能将这四项当作互斥的四个目录。

## 2. 我要做什么，去哪里找

| 任务 | 首先查阅 | 继续查阅 |
|---|---|---|
| 了解系统架构、模型、原语和主链 | [架构索引](../architecture/README.md)、[核心模型](../architecture/core-model.md)、[系统边界](../architecture/system-scope-boundary.md) | 对应 ADR；方案目标与代码事实分别确认 |
| 开发或修改业务功能 | [设计索引](../design/README.md) | 相关架构、API、SDK、运行手册与所属阶段方案 |
| 查询数据库表、关系、索引与分区 | [数据库目录](../design/database-schema-guide.md) | db/migration/ 实际迁移、相关 Mapper、分区/迁移 Runbook；设计稿不替代实际 DDL |
| 前后端接口或 SDK 对接 | [API](../api/README.md)、[SDK](../sdk/README.md) | 配对前端生成类型、调用方与接口契约 |
| 本地部署、构建、配置或故障处理 | [运行手册](../runbook/README.md) | 环境变量、配置生命周期、CI 和对应故障剧本 |
| 写测试、准备共享数据 | [测试方法](../testing/README.md)、[测试数据指南](../testing/test-fixture-guide.md) | 根 test-data/；模块专用资源仍在 src/test/resources/；跨模块 classpath 资源用 batch-test-support |
| 查看当前整改事项 | [TODO Master](../plans/todo-master.md) | [持续硬化台账](../plans/hardening-backlog.md)、[阶段方案](../plans/README.md) |
| 发起功能改造或技术可行性探索 | [阶段方案](../plans/README.md)、既有 ADR | 实测结果进 verifications/；采纳的长期决定进入 ADR/设计；不新增 spike/ |
| 查某次代码审查或问题盘点 | [代码审查](../review/README.md)、[审计与评估](../audit/README.md) | 报告结论只适用于它的基线；当前状态回看 TODO Master |
| 查测试、容量、灾备或兼容性结果 | [验证证据](../verifications/README.md) | 对应测试/运行方法、构建、环境、负载、采样窗口与限制 |
| 查代码规约、治理门禁或统计 | [规范](README.md)、[机器契约](../governance/README.md)、[当前统计](../stats/README.md) | machine baseline 与规则分开维护；不得把候选数量当作缺陷数 |
| 追溯旧方案或已结束阶段 | [归档索引](../archive/README.md) | 历史文档不能直接当作现行实现或执行步骤 |

## 3. 系统改了什么，应同步哪些文档

下表是影响范围检查表。只更新实际受影响的资产，不能机械重写所有目录；没有契约或行为变化时，不虚构 API、SDK 或生产影响。

| 改动 | 应更新的原文档资产 | 按需新增/追加的记录 |
|---|---|---|
| 架构、系统边界、模型或原语 | architecture/ 中对应说明；长期选择写/修订 ADR | 跨模块方案进 plans/；审计/验收留日期记录 |
| Trigger、业务日、Workflow、作业依赖、重放/跳批、状态与恢复 | architecture/ + 对应 design/；受影响 API/SDK 与操作手册 | plans/ 的范围/矩阵/执行日志，真实验证结果；不能只更新测试结论 |
| Worker、分区分片、claim/report、租约、Outbox、执行进度 | 对应架构/设计；wire protocol 或 SDK 变更才更新 api/、sdk/ | 受影响场景、兼容/恢复验证与验收矩阵 |
| 表、字段、约束、索引、分区、归档或清理 | 数据库目录/治理设计；迁移、分区、恢复 Runbook | 迁移审查、真实 SQL/事务/恢复证据；保持已发布迁移校验和 |
| Console API、认证、权限、导入导出格式 | api/ 权威契约；配对前端类型/调用方和相关使用说明；受影响 SDK | 契约审查、配置包/端到端验证 |
| 环境变量、配置、默认值、启动与部署 | runbook/ 的配置/环境/部署说明；实际机器注册表 | 环境对齐检查和目标环境结果分别记录 |
| 日志、指标、告警、通知或采集观察链 | runbook/ 的日志/观测/SLO 及相关架构边界 | 阈值、告警触发/恢复、接收端与业务关联证据 |
| CI、门禁、本地钩子、生成器和安全扫描 | scripts/ci/README.md、runbook/ci.md、standards/ 守护总账；相关机器契约 | 路由正反例、执行结果、失败首因和未验证边界 |
| 测试方法或 fixture | testing/ 方法与根 test-data/ 数据说明；同步脚本/生成器/测试/门禁路径 | 日期化验收结果；原始自动产物放 reports/、logs/ 或 build/ 对应位置 |
| 纯代码规约/可读性整理 | 相关规范或治理事项，仅在规则确有变化时修订规范 | 单次代码审查/治理记录，系统问题与规范问题分开记 |

资产内容更新、方案/矩阵状态、执行证据、当前事项和必要的 Changelog 要形成闭环。根 CHANGELOG.md 记产品行为，docs/changelog.md 记工程/文档基线；不把完整证据重复粘贴到多处。

## 4. 结束前核对

1. 每个受影响概念只有一个当前权威入口；其他文档引用它，不复制一套可独立漂移的规则。
2. 当前资产已反映实际改动；方案目标、已实现、本地验证与目标环境验证分开陈述。
3. 阶段方案更新原文件、日志追加批次、每轮审查/验收按日期留存，剩余事项回写台账。
4. 改名或迁移时更新索引、相对链接、代码/脚本/Skill、生成器和 CI 路由；数据资产迁移还应验证内容等价与消费契约。
5. 当前顶层目录不再新增 analysis/、backlog/、spike/、test-data/；根 test-data/ 是可执行测试资产，不属于 docs/。API 黄金样本仍属于 api/ 的机器契约，不与场景测试数据混同。
