# 文档治理规范

> 本文是仓库文档状态、待办和历史快照的维护规则。它不替代 `docs/agent-baseline.md` 的工程约束。
>
> 最后核查：2026-10-08

## 1. 权威入口

| 内容 | 唯一入口 | 说明 |
|---|---|---|
| 当前架构事实 | `docs/architecture/architecture-truth.md` | 稳定入口，指向代码、部署配置和当前架构文档；不复制易漂移统计 |
| 当前问题与待办 | `docs/analysis/todo-master.md` | 唯一当前事项索引；专题计划和 ADR 提供设计依据 |
| 当前硬化事项 | `docs/analysis/hardening-backlog.md` | 仅维护仍有效的工程硬化项及其证据要求 |
| 历史分析与修复记录 | 日期快照及归档报告 | 保留当时结论，不代表当前代码状态或待办 |
| 测试覆盖与发布门禁 | `docs/testing/` | 以最新验证记录和门禁脚本为准 |
| 运维操作 | `docs/runbook/` | 必须标注适用环境、前置条件和回滚 |
| 历史证据 | `docs/archive/` | 只读，不参与当前待办统计 |

## 2. 状态分类

每个事项只能属于以下一种状态：

- **当前待做**：代码、文档或测试尚未完成，且当前仍计划执行。
- **外部阻塞**：本地材料已准备，但依赖运维、DBA、业务方、staging 或凭据；必须写明阻塞方和解除条件。
- **暂缓**：已经做出不立即实施的决策；必须写触发条件和复审周期。
- **不做**：明确超出系统边界或收益不足；必须写理由，不能使用“待办”措辞。
- **已完成**：必须给出 commit、PR、测试或验证记录至少一种证据。
- **历史记录**：只描述过去时点；可按目录索引策略留在带日期的快照目录或移入 `docs/archive/`，必须明确标注日期和非当前权威属性，不得作为当前状态引用。

“未覆盖”“尚未验证”只有在对应验证范围仍然有效时才算当前待做；如果只是历史测试快照，必须加“历史快照”标识。

## 3. 评估、审计与审查报告

- 报告必须注明评估日期、代码基线（commit/PR/分支）、范围与排除项、采用的方法，以及证据链接。
- 结论按证据层级分别描述：设计/文档覆盖、代码已实现、自动化测试通过、真实依赖或目标环境验证；不得用较低层级证据推导较高层级结论。
- 容量、可用性、安全和生产就绪结论必须写明测试环境、负载或威胁模型、验收标准及限制。静态检查、模拟测试和本地容器结果不能表述为生产验证。
- 当前状态必须以本轮可核对的代码、配置、CI 结果和运行证据为准。日期报告保留当时结论；如被后续事实替代，应标明历史属性并链接当前权威入口，不直接改写成当前结论。
- 能力评估要区分“方案具备设计覆盖”与“系统已交付并验证”，并列明尚缺的实现、测试或环境证据。

## 4. 发布站过滤

仓库文档是否保留与是否进入统一文档站是两个维度。`docs/.docsignore` 维护不发布的文件或目录前缀，适用于已被替代且无现行依赖的历史页、技术试验、测试数据、规模统计和一次性验证证据。

- 每行一个相对 `docs/` 的文件或目录前缀，允许空行和 `#` 注释。
- 不支持通配符、绝对路径和 `..`；非法规则必须让构建失败。
- 排除只影响统一 VitePress 站和搜索索引，不删除源文件，也不改变当前待办或权威文档的归属。
- 现行架构、API、设计、测试、SDK、运维、合规、工程规范及其可追溯证据不得为了缩小站点而排除；新增规则前应检查保留文档对目标路径的引用。
- 调整规则后必须在配对前端仓执行 `npm run docs:build`，并核对生成目录中目标路径不存在。

## 5. 更新规则

1. 新事项先登记到 `docs/analysis/todo-master.md`，再在主题文档补充详情；不直接散落创建无索引 TODO。
2. 完成事项同步更新来源文档、`todo-master.md` 和必要的 `docs/changelog.md`，并删除或改写旧的“未完成”表述。
3. 每条当前事项必须包含：负责人边界、优先级、证据路径、最后核查日期、下一步或阻塞条件。
4. 计划文档完成后保留决策和验收结果；剩余事项转入 `todo-master.md`，计划正文不能继续伪装成当前清单。
5. 日期快照、一次性审计、被新版取代的方案移入 `docs/archive/`，归档文件不再修正正文。
6. 文档只使用仓库相对链接，不写本机绝对路径；示例凭据、令牌和固定密码必须使用占位符。

## 6. 项目介绍与索引维护

文档入口必须按“读者路径”维护，而不是只堆文件列表。

| 入口 | 维护责任 |
|---|---|
| 根目录 `README.md` | 说明项目做什么、解决什么问题、核心架构、快速开始，并保留 `docs/README.md`、文档治理和 runbook 入口 |
| `docs/README.md` | 文档总导航；只覆盖一级目录、顶层文档、重要专题入口和角色路径，不扁平展开全部二级文档 |
| 子目录 `README.md` | 该目录的人读索引；新增当前有效的同级文档时必须列入，归档/历史目录除外 |
| `docs/runbook/README.md` | 运维 SOP 导航；新增部署、容量、灰度、应急、配置治理文档时必须同步 |
| `docs/audit/convention-drift-guard-index.md` | 守护总账；新增系统性约束或 CI 守卫时必须同步 |
| `scripts/ci/README.md` | 可执行门禁说明；新增 `check-*` / `validate-*` 脚本必须登记 |

索引文字要求：

- 介绍页要回答“这是什么、解决什么问题、怎么运行、到哪里查设计/运维/测试证据”。
- 索引页按层级维护：一级入口覆盖二级目录，子目录入口覆盖本目录文档；不要在 `docs/README.md` 扁平展开 300+ 个文档。
- 索引页要按受众或场景分组，不用纯字母序堆积。
- 子目录 README 只放当前有效入口；历史快照放 `docs/archive/` 并标明只读。
- 重要文档移动时同步修代码注释里的 `docs/...` 引用，避免注释链接失效。
- 一次性验收报告、压测报告、排查记录放 `docs/verifications/` 或 `docs/archive/`，不要放入总入口正文。

## 7. 扫描与验收

文档复扫至少执行：

```bash
rg -n -i --glob '*.md' \
  '(TODO|FIXME|TBD|待办|未完成|未实现|暂缓|未覆盖|未验证|尚未)' docs
```

扫描结果必须排除 `docs/archive/` 后再分类，不能把命中数直接当作当前待办数。提交前还要检查：

- `todo-master.md` 的事项是否都能定位到来源文档或证据；
- 当前文档是否仍引用已归档文件中的“未完成”结论；
- 同一事项在测试、运维、架构文档中的状态是否一致；
- “不做 / 暂缓”是否有触发条件，避免后续被误实现。

运行配置与路径还必须通过：

```bash
bash scripts/ci/check-hardcoded-runtime-config.sh
bash scripts/python.sh scripts/ci/check-docs-structure.py
bash scripts/python.sh scripts/ci/check-code-doc-references.py
```

该门禁检查当前文档的个人绝对路径、运维旧端口、local profile 固定 Redis 地址、Kafka
容器 CLI 路径散落和可变 Sonar 镜像。`docs/archive/` 是只读历史证据，不追溯改写。

文档结构门禁检查主目录 README、总索引覆盖、仓库内相对链接、Finder 元数据和带日期的本机
验收报告。外部 URL 不联网检查，避免第三方站点波动阻断 CI。

## 8. 维护责任

代码变更作者负责同步直接受影响的文档；PR 审核者负责检查状态和证据是否更新。每次版本发布前复扫一次，重大架构或安全变更后立即复扫。
